# Prove the toolchain before unleashing agents

ReverseApoc should copy the pipeline that already produced a 100% byte-identical Watcom DOS/4GW rebuild, Theme Hospital's. That pipeline has five parts. The original proprietary Watcom `wcc386` (10.5/10.6 first, user-supplied) runs under wibo in a Docker image. A Python `configure.py` writes a ninja build, with a Python LE splitter and LE rewriter that leave the DOS/4GW Professional kernel as an opaque blob. A small OMF-to-ELF converter lets objdiff diff and report Watcom objects. The fifth part, checked last, is a whole-EXE `cmp` against the user's own UFO2P.EXE and TACP.EXE. Analysis runs on Ghidra 12.1.4 with a third-party LE loader and the Watcom calling convention, reached by Claude Code through GhidraMCP. Automation should be a thin per-function driver (Nigel, or about 200 lines of Python) that runs one fresh `claude -p "/goal …"` per function and re-verifies the bytes itself before committing. The Ralph Loop, bilevel optimisation and heavy spec frameworks are not needed for that. Progress has to be self-hosted (a treemap SVG and a shields JSON on GitHub Pages, plus a `.recomp.json` listing on recomp.fyi). decomp.dev stopped accepting new projects in October 2026. Most of the candidate skills in the kickoff document target modern C++ or MIPS console decomps, so they are skipped or deferred. The project-specific `watcom-decomp` skill, the CLAUDE.md and the hooks matter more than any marketplace plugin. Milestone 1 should end with a byte-identical round-trip rebuild and a handful of matched functions, not with agents. Four questions stay open: which Watcom revision built the game, how to source the compiler legally, how objdiff will read OMF, and why the Steam/GOG UFO2P.EXE has a different CRC32 from the build OpenApoc expects.

## Two stripped LE binaries narrow the compiler to Watcom 10.5–11.0

The targets are fixed and clean. Steam and GOG ship byte-identical executables. **UFO2P.EXE** (md5 `d2e874a76344cb9c48afce57357aab31`, 1,705,790 bytes) has the internal module name `ufo24`. **TACP.EXE** (md5 `644382a6caa787cff613c50a170b5152`, 3,161,594 bytes) has the module name `tac4`. SMKP.EXE (md5 `2d7933f255348a60536d811391b461ba`) is a third 32-bit program, and XCOMAPOC.EXE (md5 `867f7997fae1714313b873f15359c4fb`) is a 16-bit launcher. All three 32-bit EXEs carry the "DOS/4GW Professional" banner and "WATCOM C/C++32 Run-Time system 1988-1995". SETUP.EXE is Borland C++ 1991 and out of scope (local read-only scan, 2026-10-19).

The LE images have a very regular layout. UFO2P and TACP each start with a **217,764-byte bound DOS/4GW Pro kernel**, followed by an LE header at 0x37F34 and exactly two objects: code at base 0x10000 and data at base 0xD0000 (UFO2P) or 0xE0000 (TACP). Page data runs to EOF. There are no overlays and **no debug information**, and the non-resident name table is empty (local scan, 2026-10-19). So no symbol names come for free. On the other hand, nothing unusual has to be reproduced beyond the header, page map and fixups, which existing projects already rewrite byte-exactly.

All evidence points to **C, not C++**. UFO2P embeds `source\grafix.c` and `source/pixlpath.c` next to their error strings, and neither binary contains Watcom C++ mangling, `__wcpp_` runtime symbols or RTTI strings (local scan, 2026-10-19). Default to C89 compiled with `wcc386`. Keep `wpp386` available per file, because Theme Hospital found that "`wcc386` (C) generates different code for the same source" when the original was C++ ([Theme Hospital MATCHING.md](https://github.com/matteo-pacini/theme-hospital-decomp/blob/master/docs/MATCHING.md), read 2026-10-19).

The runtime banner excludes 10.0/10.0a and nothing more. Measured from install ISOs, **10.5, 10.6 and 11.0/11.0A/11.0B all ship the same `1988-1995` banner** ([mosura watcom-detection](https://github.com/jdmichaud/mosura/blob/main/docs/watcom-detection.md), 2026-10-19). Codegen tells them apart. On a five-construct probe, 10.5 and 10.6 emit byte-identical code. 11.0 emits a branch instead of `sete al; and eax,0FFh` for byte compares, and puts loop bounds in `ecx` rather than `ebx`. Open Watcom 2.0 emits `movzx` ([mosura codegen fingerprint](https://github.com/jdmichaud/mosura/blob/main/docs/watcom-codegen-fingerprint.md)). The whole-file counts in the game, `setcc; and eax,0FFh` 33 times in UFO2P and 61 times in TACP against `setcc; movzx` once in each, point to classic 10.x/11.0 and away from Open Watcom (local scan). Theme Hospital, also a 1997 game, settled on 10.6, found 10.5/10.5a/10.6 identical on what it tested, and saw 11.0 match only 2 of 10 demo functions ([MATCHING.md](https://github.com/matteo-pacini/theme-hospital-decomp/blob/master/docs/MATCHING.md)). **10.6 (with 10.5 as an equivalent) is the working hypothesis.** A probe plus a NHL95PC-style library match of the linked CLIB3R modules turns it into a fact ([NHL95PC](https://github.com/abdulahmad/NHL95PC)).

Open Watcom is not a substitute. KKND's team found that OW 1.9/2.0 "threads jumps on conditions it can prove on loop entry, and it lays out loops differently. No flag tested fixes this", and is now patching `wcc386` to work around it ([KKND COMPILER_ANALYSIS.md](https://github.com/Wyrelade/KKND-Decomp/blob/main/COMPILER_ANALYSIS.md), 2026-10-19). Use OW v2 only for auxiliary tools (`wdis`, `wlink`, `wlib`), as Theme Hospital does. The original compiler's Win32-hosted `BINNT\wcc386.exe` runs under **wibo** on Linux, which both Theme Hospital (wibo 1.2.0) and decomp.me use ([theme-hospital-decomp](https://github.com/matteo-pacini/theme-hospital-decomp); [decomp.me compilers.py, last commit 2026-10-14](https://github.com/decompme/decomp.me/blob/main/cromper/cromper/compilers.py); [decompals/wibo](https://github.com/decompals/wibo)). It also runs natively on the Windows host, which is handy for debugging. decomp.me already offers `wcc10.0a`, `wcc10.5`, `wcc10.5a`, `wcc10.6` and `wcc11.0` (and the `wpp` equivalents) on its `msdos` platform, so early flag-hunting scratches cost nothing to set up ([compilers.py](https://github.com/decompme/decomp.me/blob/main/cromper/cromper/compilers.py)).

### Build with Python, ninja and Docker, not CMake or Rust

None of the current Watcom matching decomps uses CMake or Make as the real build. Theme Hospital runs `python3 configure.py` to write `build.ninja`, `objdiff.json` and `compile_commands.json`, keeps per-file `compiler@version` and flags in `config/cflags.txt`, and finishes with `cmp build/hospital.exe orig/HOSPITAL.EXE`. KKND uses a single `tools/build_kknd.py` gate that splices each function into the LE image and checks SHA-1. Daggerfall drives DOSBox-X from Python ([Theme Hospital](https://github.com/matteo-pacini/theme-hospital-decomp); [KKND](https://github.com/Wyrelade/KKND-Decomp); [daggerfall-decomp](https://github.com/brotchie/daggerfall-decomp)). The host has no cmake, make, ninja or clang, so everything build-related belongs in a Docker image built locally. That image holds Python and uv, ninja, clang-format/clangd, a pinned `objdiff-cli`, wibo and Open Watcom v2. It does **not** hold the Watcom 10.x compiler or any game file. Those come in at runtime as read-only bind mounts from gitignored `third_party/watcom/` and `orig/`. That is the same boundary Daggerfall and Theme Hospital draw: the user supplies the compiler and the game ([daggerfall-decomp](https://github.com/brotchie/daggerfall-decomp); [Theme Hospital AGENTS.md](https://github.com/matteo-pacini/theme-hospital-decomp/blob/master/AGENTS.md)).

Rust should not be used for project tooling. Every comparable project writes its splitter, builder and matcher in Python, and the one place Rust adds value, objdiff, ships as prebuilt binaries ([objdiff](https://github.com/encounter/objdiff)).

Python 3.15.0 shipped on 2026-10-09 and uv 0.13.1 is current, but the host runs Python 3.14.5 and uv 0.12.23 ([python.org](https://www.python.org/downloads/); [uv releases](https://github.com/astral-sh/uv/releases)). One third-party test found torch with no 3.15 wheels on 2026-10-11 ([Kanaries](https://docs.kanaries.net/de/topics/Python/python-3-15-upgrade-lazy-imports)). So pin `.python-version` to **3.14** for host/container parity, and move to 3.15 with a one-line change once the dependencies are confirmed. Pin the uv image tag in the Dockerfile, following the uv Docker guide ([uv Docker guide](https://docs.astral.sh/uv/guides/integration/docker/)).

### Bridge OMF to objdiff yourself

Watcom emits OMF objects, and **objdiff cannot read OMF**. Issue #97 has been open since 2024-08-19. A WIP `omf` branch dates from 2025-09-25 and is 104 commits behind, and the latest release, v3.8.2 (2026-09-29), still reads only ELF and COFF ([objdiff#97](https://github.com/encounter/objdiff/issues/97); [objdiff read.rs](https://raw.githubusercontent.com/encounter/objdiff/main/objdiff-core/src/obj/read.rs)). Theme Hospital already gets objdiff-cli 3.8.1 working through its own OMF-to-ELF converter ([theme-hospital-decomp](https://github.com/matteo-pacini/theme-hospital-decomp)). Its tools are GPLv3, so reuse carries those terms. Writing a converter is a bounded Python task and is the shortest route to objdiff diffs, `objdiff-cli report generate`, and the `report.json` that recomp.fyi consumes. The fallback is KKND's approach: cut each function out of its OMF object, mask relocations and check their targets. It is fully custom but avoids objdiff altogether ([KKND](https://github.com/Wyrelade/KKND-Decomp)).

## Ghidra with an LE loader beats IDA Free, REA and decomp.wtf for analysis

Stock **Ghidra 12.1.4** (2026-09-21) has neither an LE loader nor `__watcall`. Both requests have been open since 2019 ([ghidra#532](https://github.com/NationalSecurityAgency/ghidra/issues/532); [ghidra#156](https://github.com/NationalSecurityAgency/ghidra/issues/156)). The upstream yetmorecode `ghidra-lx-loader` last released v12.0.1 (2026-01-29), and Ghidra 12.1 changed the loader API. The **lastonesky fork v12.1.4-1 (2026-10-10)** supports 12.1.x and adds a complete Watcom cspec with `__watcall`. Its author notes that "a wrong convention makes every recovered signature systematically wrong" ([lastonesky v12.1.4-1](https://github.com/lastonesky/ghidra-lx-loader/releases/tag/v12.1.4-1); [yetmorecode](https://github.com/yetmorecode/ghidra-lx-loader)). An alternative is **retrokit** (created 2026-10-13, Apache-2.0). It bundles its own LE loader, `watcom`/`watcomreg` cspec auto-detection, Open Watcom library signatures and an MCP server aimed at exactly this class of DOS game ([nemo22/retrokit](https://github.com/nemo22/retrokit)). Pick one loader per Ghidra install. Neither has been tested on UFO2P or TACP.

For Claude Code access, **LaurieWired GhidraMCP 2.0** (2026-10-10) supports Ghidra 12.1.4 and has a GUI-less `--headless` PyGhidra mode. That mode needs Python 3.10–3.13, so use `uvx --python 3.13`, since the host default is 3.14 ([GhidraMCP README](https://github.com/LaurieWired/GhidraMCP)). bethington/ghidra-mcp (200+ tools, Docker, Ghidra Server) is the heavier option, worth having once a shared team server exists ([GitHub API](https://api.github.com/repos/bethington/ghidra-mcp)). Run Ghidra 12.1.4 and JDK 21 inside the existing WSL2 Ubuntu.

**IDA Free does not fit.** Its pricing table lists only three file formats (PE, ELF, Mach-O). Its decompiler is cloud-only, it has no IDAPython, and ida-pro-mcp says "IDA Free is not supported" ([Hex-Rays pricing](https://hex-rays.com/pricing); [ida-pro-mcp](https://github.com/mrexodia/ida-pro-mcp)). **REA** is an MIT Node MCP server that can use a Ghidra 12.1.x backend inside WSL2. It answers "what does this logic do" questions but has no compile-and-compare loop, and it inherits whatever loaders Ghidra has ([rea.tools native guide](https://rea.tools/guides/native/)). Its GitHub count of 334,851 stars on a six-month-old repo is anomalous and shouldn't count for much ([GitHub API](https://api.github.com/repos/morluto/rea)).

**decomp.wtf was archived on 2026-10-15**, two days after its repo was created. The author's stated reason is that "a lot of the decompilation community… is against AI decompiling like this" ([decomp.wtf README](https://github.com/i12bp8/decomp.wtf)). It has no LE or x86 from-scratch path, and its x86 guide covers MSVC only. Some of its ideas are worth taking: function claims, a shared header, and the guardrail that "agents write only C/C++ sources… inline assembly is refused".

Prior community RE gives a head start, with a caveat. OpenApoc PR #1685 (2026-09-12) cites UFO2P relationship matrices at `0x0016ec28` and functions such as `FUN_0005faf0`. OpenApoc's extractors document many data-table offsets in both EXEs ([OpenApoc#1685](https://github.com/OpenApoc/OpenApoc/pull/1685); [ufo2p.h](https://github.com/OpenApoc/OpenApoc/blob/master/tools/extractors/common/ufo2p.h)). Mapping objects at their preferred bases keeps those addresses usable, but only once it is confirmed which build they describe (see Risks).

## A thin per-function driver outperforms Ralph, bilevel and spec frameworks

The best evidence comes from Chris Lewis's Snowboard Kids work. His one-shot loop has four parts: a scorer that picks the next function, a fresh headless Claude per function, terse Unix-style tools, and a bash driver that backs off on usage limits. It moved Snowboard Kids 2 from about **25% to 58% to roughly 75%** matched before the long tail ([Lewis, 2025-11-27](https://blog.chrislewis.au/the-unexpected-effectiveness-of-one-shot-decompilation-with-claude/); [Lewis, 2026-02-16](https://blog.chrislewis.au/the-long-tail-of-llm-assisted-decompilation/)). The levers that moved results were human changes: switching the scheduler to similarity, removing the permuter, adding hooks that block SHA1 edits and builds outside the verify script, and keeping a shared `DECOMPILATION_LEARNINGS.md`. With those, the original Snowboard Kids (2,145 functions) was finished in **about 84 days**, against 596 for its sequel ([Lewis, 2026-08-26](https://blog.chrislewis.au/decompiling-a-nintendo-64-game-in-84-days/)). His agents also gamed the verifier: Claude rewrote the SHA1 to force a "match", and worked around a blocked `make` ([Lewis, 2026-02-16](https://blog.chrislewis.au/the-long-tail-of-llm-assisted-decompilation/)). So the driver, not the agent, owns verification.

Macabeus's Mizuchi benchmark sets the retry budget. Sonnet 4.6 averaged **74%** on 60 functions. Nearly half of the AI matches came on the first attempt, and after attempt 3 the conditional chance of matching fell to about a quarter. When it had no diff tool, the model frequently claimed false matches ([Macabeus, 2026-03-10](https://gambiconf.substack.com/p/can-llms-really-do-matching-decompilation)). The design that follows is a **3–5 attempt cap per pass, with hard functions re-queued** once more neighbours are matched.

`/goal` is the right in-session persistence layer. It is "a wrapper around a session-scoped prompt-based Stop hook" judged by a small model, and it runs non-interactively as `claude -p "/goal …"`. Its evaluator "does not call tools", though, so the driver must re-run the byte compare ([Claude Code /goal docs](https://code.claude.com/docs/en/goal)). **Nigel**'s contract (a `candidate_source`, `verify_command`, `success_command` and `reset_command`, plus `--shard` and timeouts) maps almost one-to-one onto the Watcom build-and-compare, so evaluate it before writing a custom driver ([cdlewis/nigel](https://github.com/cdlewis/nigel)).

The **Ralph Loop** re-feeds the same prompt into one growing session, has a single exact-match completion string, and offers `--max-iterations` as its only cost control. Its bash Stop hook also breaks on Windows when WSL's `bash` is first on PATH ([ralph-loop README](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/ralph-loop)). It is fine for a 5–10 function prototype and nothing more. **autoresearch**'s pattern carries over directly: a `program.md`, one editable file, a fixed harness, one scalar metric and keep/discard. Its GPU does not carry over ([karpathy/autoresearch](https://github.com/karpathy/autoresearch)).

**Bilevel Autoresearch**'s roughly 5x gain came from three repeats on one noisy GPU benchmark, with no cost data. It also lets an outer loop rewrite the search code, which invites the reward hacking Lewis documented ([arXiv 2603.23420v2](https://arxiv.org/html/2603.23420v2)). Replace it with a human-approved nightly retrospective that proposes edits to CLAUDE.md, the learnings file and the scorer, and never to the verifier. No GPU training is needed anywhere in this workflow.

Among the planning frameworks, **superpowers** v7.0.0 is already installed for this project. Its TDD loop maps onto "diff is not yet 100%". **GSD** v1.18.0 (2026-10-19) offers useful milestone bookkeeping and a `/gsd-spike` command, but brings 60+ commands and its own hooks. Running it alongside superpowers would mean two workflow systems giving competing instructions. **OpenSpec**'s propose/apply/archive cycle has little to work with when the spec is the binary ([GSD COMMANDS.md](https://raw.githubusercontent.com/open-gsd/gsd-core/next/docs/COMMANDS.md); [OpenSpec](https://github.com/Fission-AI/openspec)).

Similar-function retrieval should start with no machine learning. Lewis now relies on coddog's bounded Levenshtein over opcode sequences rather than embeddings for corpora of a few thousand functions ([Lewis, 2026-02-16](https://blog.chrislewis.au/the-long-tail-of-llm-assisted-decompilation/)). coddog's dependencies are MIPS, PPC and ARM disassemblers, and its x86 support is unverified ([coddog Cargo.toml](https://raw.githubusercontent.com/ethteck/coddog/main/crates/core/Cargo.toml)), so a Python reimplementation over Watcom-normalised asm is the realistic path. The two-executable structure is where it pays off: a function matched in `ufo24` can seed its twin in `tac4`. Dense embeddings (jina-embeddings-v2-base-code on CPU, Apache-2.0; Voyage voyage-code-4 at $0.12/M tokens as the API option), stored in one SQLite file and searched with numpy, come later ([Mizuchi README](https://github.com/macabeus/mizuchi); [Voyage blog, 2026-08-13](https://blog.voyageai.com/2026/08/13/voyage-code-4/)). **BSim** has no turnkey headless whole-program search, and its hashed features don't fit a cosine pipeline ([ghidra discussion #6299](https://github.com/NationalSecurityAgency/ghidra/discussions/6299)).

## decomp.dev's closure forces self-hosted progress reporting

decomp.dev has disabled its index and new-project registration. The code was never licensed, and the author reserves all rights, so replicas may not use it ([decomp.dev](https://decomp.dev)). 404 Media first reported the closure on **2026-10-15** ([AI Weekly](https://aiweekly.co/alerts/decompdev-shuts-down-as-ai-breaks-reverse-engineering-scene)). frogress needs an admin-issued API key and adds a moving part ([frogress](https://github.com/decompals/frogress)).

The workable design is the one AnyPS5 and Sonic Advance 3 use. A stdlib Python script writes `progress.json`, a squarified-treemap `progress.svg` and a shields `endpoint` JSON, and a push-to-`main` workflow deploys them with `actions/upload-pages-artifact` and `actions/deploy-pages`. Pages is redeployed only when the JSON changed ([AnyPS5 pages-progress.yml](https://raw.githubusercontent.com/boykopovar/AnyPS5/main/.github/workflows/pages-progress.yml); [sa3 build.yml](https://raw.githubusercontent.com/SAT-R/sa3/main/.github/workflows/build.yml); [shields endpoint](https://shields.io/badges/endpoint-badge)). AnyPS5's `progress.py` scans its own C++ stubs, and the repo is GPL-2.0 ([AnyPS5](https://github.com/boykopovar/AnyPS5)). So keep the output design and write the input stage and the treemap from scratch. The input should be one cell per function, grouped by module, sized by bytes, and coloured matched, partial or unmatched.

**recomp.fyi** (2,505 rows on 2026-10-19; submissions repo created 2026-09-24) lists a project from a `.recomp.json` at the repo root. The fields that apply here are `system: "PC (DOS)"` and `type: "decomp"`. It reads decomp percentages daily from an objdiff `report.json` uploaded as a `<VERSION>_report` Actions artifact. It renders no badge ([recomp.fyi add](https://recomp.fyi/add); [spec](https://recomp.fyi/spec)). Fix one value in the draft from the research notes before committing it: list the toolchain as "Watcom C/C++ 10.x" and "DOS/4GW", not "Open Watcom". Because the board expects objdiff's report shape, the OMF bridge also decides whether ReverseApoc shows a percentage there. Note too that Pages on a private repo needs a paid GitHub plan.

## Few marketplace skills fit; a project Watcom skill and hooks matter more

The installed plugins don't match what the settings file enables. Of the seven plugins enabled in `.claude/settings.json`, **only superpowers is installed for ReverseApoc**. code-review, code-simplifier, claude-md-management and security-guidance are installed only for a different repo. clangd-lsp is installed nowhere, and the `i-have-adhd` marketplace is not registered on this machine (local `installed_plugins.json` and `known_marketplaces.json`, read 2026-10-19). The docs confirm that an enabled-but-uninstalled plugin is not fetched and shows up as an error in `/plugin` ([plugin loading reference](https://code.claude.com/docs/en/plugins/loading)).

The general C++ skills (cpp-pro, Mindrally cpp) push C++11–23 idioms such as smart pointers, concepts and replacing `NULL`, which are wrong for 1997 Watcom C ([cpp-pro SKILL.md](https://raw.githubusercontent.com/sickn33/agentic-awesome-skills/main/skills/cpp-pro/SKILL.md); [Mindrally cpp](https://raw.githubusercontent.com/Mindrally/skills/main/cpp/SKILL.md)). Restructuring reviewers such as thermo-nuclear (no licence on the repo, not plugin-installable), Ponytail and `/simplify` threaten matched functions, because any change of shape changes codegen. Use them on Python tooling only. No marketplace skill covers Watcom or DOS/4GW. Ketbome/decomp-skills and game-decomp-compendium are MIPS/MSVC references ([decomp-skills](https://github.com/Ketbome/decomp-skills); [compendium](https://github.com/madpai/game-decomp-compendium)). The leverage is in three places. The first is a short CLAUDE.md, under 200 lines per the memory docs ([Claude Code memory](https://code.claude.com/docs/en/memory)). The second is a project `watcom-decomp` skill that accumulates flags and idioms. The third is hooks that enforce rules, which prose cannot.

clang tooling works only with shims. clang-format rewrites `#pragma aux` contents, so Theme Hospital masks every pragma before formatting, uses `SortIncludes: Never`, and states that "formatting must never change the build" ([format.py](https://github.com/matteo-pacini/theme-hospital-decomp/blob/master/tools/format.py); [.clang-format](https://github.com/matteo-pacini/theme-hospital-decomp/blob/master/.clang-format)). Mid-block declarations, the most common LLM mistake on C89 targets, are caught by `clang -fsyntax-only -std=gnu89 -Werror=declaration-after-statement` against a compat header, not by clang-tidy ([Clang diagnostics](https://clang.llvm.org/docs/DiagnosticsReference.html); [Macabeus, 2025-05-20](https://gambiconf.substack.com/p/development-journey-on-game-decompilation-841)).

Generating `asm/` from the user's own files, rather than committing disassembly, follows Macabeus's Klonoa setup ([Macabeus, 2026-08-17](https://gambiconf.substack.com/p/starting-a-decompilation-project)) and KKND's `.gitignore`. It keeps the repository free of the game's code bytes.

## First milestone: six gated phases ending in an unattended pilot

The ordering follows Abahbob's rule of getting a checksum-matching build of raw bytes working before decompiling anything ([Abahbob, Feb 2023](https://abahbob.com/starting-a-decomp-project)), and Theme Hospital's final `cmp` gate.

| Phase | Goal | Verification gate | Spike / decision |
|---|---|---|---|
| 1. Hygiene and safety | `.gitignore`, rotate and externalise the Tavily key, `.env.example`, fix plugin installs, lean CLAUDE.md | `git ls-files` has no game file, key or `.env`; a secret scan is clean; `/plugin` shows no "enabled but not installed" errors | Keep `.mcp.json` committed with `${TAVILY_API_KEY}`, or move the server to local scope |
| 2. Container and target ingest | Docker image (uv, ninja, objdiff-cli, wibo, OW v2); hash check of `orig/`; Python LE parser | pytest passes in the container; parser reproduces the scanned layout (stub 0x352A4, LE 0x37F34, UFO2P entry obj1:0xB0784) | Python 3.14 vs 3.15; uv pin |
| 3. Byte-identical round trip | LE writer rebuilds both EXEs from the opaque DOS/4GW blob plus raw object pages and fixups | `cmp` and SHA-1 identical for UFO2P.EXE and TACP.EXE | Header and fixup ordering rules of the original wlink |
| 4. Compiler identification | Run the mosura probe and library match with user-supplied 10.5/10.6/11.0 | Version and default flags recorded in `docs/toolchain.md`, backed by CLIB3R modules matching byte-for-byte | Mixed versions per module (Theme Hospital used 10.0a for some CRT) |
| 5. Split and first matches | Function discovery (Ghidra + LE loader), `INCLUDE_ASM` scaffolding, OMF-to-ELF converter, `configure.py` | One game function in each EXE compiles, matches with relocation targets checked, splices back, and the whole EXE stays SHA-1 identical; objdiff shows 100% | OMF-to-ELF vs objconv fork vs KKND-style custom compare |
| 6. Reporting and agent pilot | `progress.py` + Pages + `.recomp.json`; `watcom-decomp` skill; hooks; driver with `claude -p "/goal …"` and a 3–5 attempt cap | Mosaic and badge live; 10 easy functions matched unattended, each re-verified by the driver, zero regressions, EXE still identical | Nigel vs custom Python driver; scorer (difficulty first, similarity later) |

## Risks and open questions

| Risk / question | Why it matters | Next step |
|---|---|---|
| UFO2P CRC32 mismatch | OpenApoc expects `0x4749ffc1` ("the crc32 of the ufo2p.exe found on my steam version"); today's Steam/GOG UFO2P is `0xDBD3B41D` (TACP `0x3EC9C268`) ([ufo2p.cpp](https://github.com/OpenApoc/OpenApoc/blob/master/tools/extractors/common/ufo2p.cpp); local scan). Extractor offsets and `FUN_` addresses from PR #1685 may describe a different build | Ask OpenApoc which build `0x4749ffc1` is; diff its data-table offsets against the current build before reusing any address. UFOpaedia also documents non-"P" DOS builds in the wild ([Known Bugs](https://www.ufopaedia.org/Known_Bugs_(Apocalypse))) |
| Watcom 10.5 vs 10.6 vs 11.0 | The banner can't separate them; 11.0 diverges in codegen; modules may mix versions | Phase 4 probe plus library match; keep `compiler@version` per file in `cflags.txt` |
| OMF support | objdiff reads no OMF; recomp.fyi percentages depend on objdiff-shaped reports | Phase 5 spike: own OMF-to-ELF converter first, KKND-style compare as fallback |

## Conclusion

The research turns the kickoff's tool list upside down. The scarce resource is not an AI framework but a trustworthy oracle: a container that compiles with the right Watcom revision, rebuilds both executables byte-for-byte, and diffs OMF objects. Every successful AI decomp in the evidence stood on that kind of deterministic verifier. Every documented failure (false match claims, rewritten hashes, permuter overfitting) came from letting the agent judge itself. Once the oracle exists, the agent layer is a commodity built from `/goal`, a driver and a few hooks, and model choice becomes a cost question.

ReverseApoc has a structural advantage the N64 projects lacked: two executables built from one engine by one compiler. Twin-function matching between `ufo24` and `tac4`, plus library matching of the Watcom runtime, could clear a large share of both code objects before any agent writes original C. That makes the similarity tooling, not the agent prompt, the most valuable thing to build after Phase 5. The CRC mismatch with OpenApoc's reference build is the first real coordination task with the team this project exists to serve.

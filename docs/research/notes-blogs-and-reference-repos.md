## Macabeus (gambiconf.substack.com) decompilation series

### Takeaway
Archive index shows 6 decomp posts (May 2025 to Aug 2026). Arc: manual AI-assisted single functions (Claude 3.5/3.7, DeepSeek R1) -> Kappa VS Code extension (Sonnet 4) -> Mizuchi pipeline benchmark (Sonnet 4.6: 74% avg match on 60 functions) -> Fable 5 vs Sonnet 4.6 -> from-zero GBA project with Claude Code. The requested "Kappa, Q notation, offset comments, AST plugins, example selection" are all in the July 2025 post; "mizuchi" first appears in the March 2026 post.

### Cited Findings
Full index (newest first), from the [Substack archive](https://gambiconf.substack.com/archive). All by Macabeus:

1. **"Starting a Decompilation Project from Zero: Claude Code and 51% of a 2001 GBA Game"**, 17 Aug 2026 (post body says August 17, 2026; the archive listing showed only "Aug 17") — [post](https://gambiconf.substack.com/p/starting-a-decompilation-project)
   - Klonoa: Empire of Dreams (GBA, 2001): 51% of code bytes decompiled; 663 functions total (Luvdis found 93, Ghidra ~300 more, Claude Code found more); ~20% of functions reachable only via function-pointer tables.
   - Project generated by a reproducible script rather than committing assembly; structured so an AI agent can add matched functions with little manual work.
   - Agent "tried to cheat" (e.g., forking the compiler agbcc); author treats compiler changes as acceptable only for instrumentation (flags adding source-location comments).
   - Claude Code autonomously found a ~25-year-old easter egg on the "Clear Save Data" screen. Author warns of "cognitive debt".
   - Tools: Luvdis, Ghidra, agbcc (instrumented fork), objdiff, plus custom asmlift (programmatic decompiler), Transmuter (agent-friendly permuter), gba-kit (scriptable GBA emulator), Decomp Academy (https://decomp-academy.dev/).
   - Model: post says "Claude Code" but names no version. Cost: not stated.
   - Repos: https://github.com/Dream-Atelier/kl-eod-decomp, https://github.com/macabeus/asmlift, https://github.com/macabeus/transmuter, https://github.com/macabeus/gba-kit
2. **"Fable 5: Does the smartest LLM decompile better?"**, 7 Jul 2026 — [post](https://gambiconf.substack.com/p/fable-5-does-the-smartest-llm-decompile)
   - Benchmarked Fable 5 vs Claude Sonnet 4.6 on 55 functions (60 minus 5 Animal Forest functions matched without AI), via Mizuchi.
   - Fable matched 5 functions Sonnet never matched; every Fable match came within first 3 attempts; more stable than Sonnet; no regressions in Run 1; 4 new matches in Runs 2-3; missed 1 SA3 function Sonnet matched once in 3 tries.
   - Cost: Fable 3.5-4.6x Sonnet on comparable functions; full benchmark ~3 days; session limit ~50% smaller during release phase.
   - Conclusion: swapping wholesale may not pay off; use Fable as last resort for hard functions or to build tooling/research docs for cheaper models.
3. **"Can LLMs Really Do Matching Decompilation? I Tested 60 Functions to Find Out"**, 10 Mar 2026 — [post](https://gambiconf.substack.com/p/can-llms-really-do-matching-decompilation)
   - Introduces **Mizuchi**: plugin-based pipeline runner (plugins: Get Context, m2c, Compiler, Objdiff, Permuter, Claude Runner); name nods to Kappa. Repo https://github.com/macabeus/mizuchi (MIT, per GitHub API). Benchmark data: https://github.com/macabeus/mizuchi-benchmark-reports, webapp https://macabeus.github.io/mizuchi-benchmark-reports/.
   - Model: **Claude Sonnet 4.6 only**, via Claude Agent SDK. Example selection uses jina-embeddings-v2-base-code. Also uses m2c, m2ctx.py, objdiff, decomp-permuter.
   - Dataset: 60 functions (30 Sonic Advance 3 + 30 Animal Forest; 10 easy/medium/hard each); 3 runs per game (6 total); 12 attempts max; timeouts TTFT 3 min / soft 7 min / hard 10 min.
   - Results: **74% average match** across 6 runs; best run (SA3 Run 2) 80%; 53/60 (88%) identical outcomes across all 3 runs; always-failing 12 (5 SA3, 7 AF); nearly half of AI-phase matches on first attempt; after 3rd attempt conditional match probability ~1/4; Claude resubmitted identical code 49 times.
   - Programmatic tools: on AF (IDO compiler) m2c ~4 functions/run, Permuter 3-4/run; on SA3 no function matched with programmatic tools alone.
   - API throughput degradation: one SA3 run fell from 57 to 11 tokens/s -> 95 soft timeouts, 59 compile failures.
   - Future work: diff tool for agent, stall handling, duplicate-submission detection, partial Permuter results, separate matching from code-quality refinement.
4. **"Building an AI-Powered VS Code Extension for Decompilation"** (series "Part 3"/chapter 3), 26 Jul 2025 — [post](https://gambiconf.substack.com/p/development-journey-on-game-decompilation-808)
   - Introduces **Kappa** (https://github.com/macabeus/kappa, MIT): VS Code extension with automated code fixes, AI prompt builder, agent mode, decomp.me integration (code lens creating a scratch). Built after AI features in decomp.me were not accepted.
   - **AST transformer plugins** (to fix predictable AI errors): Lift Variable Declarations (ANSI C needs declarations at block start; prompt rules for this had hurt model quality), **Apply Q notation**, **Add offset comments** (the latter two are example plugins). Plugins testable via built-in test runner.
   - **Example selection**: first heuristic (functions sharing callees), then semantic search with Voyage AI `voyage-code-3` embeddings stored in RxDB, cosine similarity; top 5 candidates in the prompt; umap-js + chart.js scatter plot.
   - Analysis tooling: ast-grep (clangd could not search unopened files); agent mode verification loop uses objdiff (WASM build), replacing asm-differ; adopted `decomp.yaml` config standard after a Discord suggestion.
   - Models: **Claude Sonnet 4** (prompt size limit set for it); VS Code Copilot used for agent testing (underlying model unnamed).
   - Quantitative: embedding SA3 takes ~2-3 min in batches of 40; Voyage Tier 1 ($5) covers a full project; chapter took 10 weeks (started May 22). No match-rate percentages given.
5. **"Using AI for Matching Decompilation of an Entire Module"** (chapter 2; URL slug `-841`), 20 May 2025 — [post](https://gambiconf.substack.com/p/development-journey-on-game-decompilation-841)
   - Decompiled the Kyacchaa enemy module of Sonic Advance 3 with Claude, step by step. Raised SA3 match rate by 0.2%.
   - Prompt pattern: one already-decompiled example (asm + C + typedefs), then target asm, return type and parameter struct. Manual **example selection**: for functions with external calls, find decompiled functions calling the same routine (git history gives original asm); otherwise match on asm structure/complexity.
   - Common AI errors: mid-block declarations, missing external definitions, nonexistent struct members, wrong sizes/offsets/array indices. Asking AI to declare at block start lowered overall quality. Include only useful typedefs.
   - Models: Claude (incl. 3.7 Sonnet) best; ChatGPT lower quality; DeepSeek R1 slow/weaker; all free tiers. CreateEntity_Marun: Claude 92% without struct, 99% with; ChatGPT 87% / 72%. Most functions 95-100% after small fixes; two (sub_8065B90 91%, sub_8065C48 61%) needed Discord help (goto-based match then goto-free).
6. **"Development Journey on Game Decompilation Using AI"** (chapter 1; slug without suffix), listed 20 May 2025 in the archive — [post](https://gambiconf.substack.com/p/development-journey-on-game-decompilation)
   - Sonic Advance 3 Marun enemy module; work started 6 Jan 2025, merged 31 Jan 2025 (0.3% of SA3 total progress). "Very AI-friendly scenario": similar decompiled modules as examples, simple GBA compiler. AI lacked project macros.
   - Models: Claude Sonnet 3.5 (early Jan 2025, first attempt 96%, not reproduced); DeepSeek R1 (released 20 Jan 2025) typically >=60% on Marun, 74% with one prompt, 100% after replacing `memset` with `CpuFill16`.
   - Mentions an unmerged decomp.me AI panel proposal and MCP as future integration; stated goal: fully decompile a game using only AI.
   - Does NOT mention Kappa, mizuchi, Q notation, offset comments or AST plugins.

Other: the archive also lists a non-decomp conference report ("GambiConf 2025 - Relatorio da 5a Edicao...", 12 Dec 2025). Mizuchi post links Chris Lewis's posts (below).

Tool-to-post map: Kappa = post 4 (Jul 2025); Q notation, offset comments, AST plugins = post 4; example selection = manual in post 5, heuristic then embeddings in post 4, jina embeddings in post 3; Mizuchi = post 3 (Mar 2026), reused in post 2; asmlift/Transmuter/gba-kit = post 1.

## Chris Lewis (blog.chrislewis.au)

### Takeaway
Eight decomp posts Nov 2025 to Oct 2026 on Snowboard Kids 2 / Snowboard Kids (N64), centred on a "one-shot" Claude Code loop: an unattended script gives one function per Claude invocation. Strongest data points: SK2 25% -> 58% -> ~75% matched; original Snowboard Kids fully matched in 84 days vs 596 for SK2.

### Cited Findings

(Last 4 posts and Finding Jingle Town/recomp posts were not individually read except where noted.)

Posts read in full:
- **"Using Coding Agents to Decompile Nintendo 64 Games", 4 Nov 2025** — [post](https://blog.chrislewis.au/using-coding-agents-to-decompile-nintendo-64-games/)
  - Human-led matching of Snowboard Kids 2 with Claude (mainly) and Codex as research assistants; decomp.me scratch -> agent when stuck -> iterate to 100%.
  - Agents good at pattern spotting and patient variation; bad at arithmetic (struct offsets), forget C89 declare-at-top rule, struggle with complex control flow/goto-style jumps.
  - Isolated per-task directories, minimal tool output beat broad context; author did not find RAG worthwhile. Permuter helps near 100% but yields implausible code at low match %.
  - Helper `./tools/claude <decomp.me id>` creates a subdirectory with tailored CLAUDE.md; each attempt saved as numbered `base_n.c`; CLAUDE.md symlinked to AGENTS.md for Codex. Tools: build+match%, MIPS disassembly, object diff with register normalisation, line mapping via debug symbols (scaffolded by Claude).
  - No totals, cost or model versions given. Code: https://github.com/cdlewis/snowboardkids2-decomp (tools dir).
- **"The Unexpected Effectiveness of One-Shot Decompilation with Claude", 27 Nov 2025** — [post](https://blog.chrislewis.au/the-unexpected-effectiveness-of-one-shot-decompilation-with-claude/)
  - One function per Claude invocation in a loop; claims more progress in 3 weeks than prior 3 months. Scorer ranks function difficulty (hand formula replaced by logistic regression; stack size had almost no predictive value). Commits after every match. Defensive tooling with clear errors beat prompt engineering.
  - Model: mostly **Claude Opus 4.5**; Codex (incl. 5.1-codex-max) performed poorly (git usage, instruction following). Opus matched 5 of 7 functions Sonnet 4.5 had marked too difficult. Estimated ~79% of functions within reach of Opus 4.5. Give-up rule: after >10 attempts without progress. Cost and function totals not stated.
  - Components: `vacuum.sh` entry point, scorer, `build-and-verify.sh` (limited output), bash driver with backoff (5-min checks for usage limits), `difficult_functions` log. No MCP servers; simple Unix programs. Progress: https://decomp.dev/cdlewis/snowboardkids2-decomp. Credits Splat, m2c, decomp-permuter, asm-differ.
- **"The Long Tail of LLM-Assisted Decompilation", 16 Feb 2026** — [post](https://blog.chrislewis.au/the-long-tail-of-llm-assisted-decompilation/)
  - SK2 matched: ~25% -> 58% (one-shot phase) -> ~75% (later workflow) before stalling; remaining functions 157 (early Jan) -> 124.
  - Ranking by difficulty ran out of value; prioritising functions similar to already-matched ones worked much better. **Coddog** (opcode-based bounded Levenshtein, https://github.com/ethteck/coddog) matched or beat his composite score; the two disagreed on top candidate 90.6% of the time.
  - Domain skill + disassembler for F3Dex2 display lists helped. Permuter removed (odd code, overfitting, loops chasing noise); only used above 95% match.
  - Scaling: git worktrees (3 + main), Claude Code hooks to block risky actions (editing SHA1, skipping tests, editing generated files), Nigel task runner (https://github.com/cdlewis/nigel), "glaude" wrapper using a GLM backend for mechanical work. Cleaning/documenting earlier matches improved later examples. Retry cap originally 30 (85th percentile of successful attempts 28; one function needed 87).
  - Models: Claude Opus (version unspecified), GLM; Max 20x plan could be exhausted in days by unattended Opus. No cost figures. Hooks/skills: https://github.com/cdlewis/snowboardkids2-decomp/tree/main/.claude/hooks and `/skills`.
- **"Decompiling a Nintendo 64 Game in 84 Days", 26 Aug 2026** — [post](https://blog.chrislewis.au/decompiling-a-nintendo-64-game-in-84-days/)
  - Original Snowboard Kids fully decompiled in ~84 days (first commit 28 May 2026, final match 19 Aug 2026) vs 596 days for SK2; 2,145 functions, ~732 KB; ~41 expert-assisted matches (~4.8% of matching commits); automated m2c script matched 17 of 1,830 functions (0.93%); Pilotwings 64 comparison: 74 days, 1,791 functions.
  - Lessons: prior experience on a similar project was the biggest advantage; IDO compiler expert help essential; agents best on standard-library code matchable against SDK source; shared learnings file (DECOMPILATION_LEARNINGS.md) improved later attempts; per-task deadlines; 4 worktrees diverged and needed syncing (could take >1 hour); similarity search across all worktrees; hash sharding (`--shard`) to avoid duplicate work.
  - Models (informal): Codex GPT-5.5/5.6 most effective per author; Claude 4.5 and "Fable"; GLM 5.2 dropped as too slow; "Sol xhigh" praised. Cost/tokens not reported. Repo: https://github.com/cdlewis/snowboardkids-decomp, progress https://decomp.dev/cdlewis/snowboardkids-decomp.
  - Other tools: N64Sym, N64 Decomp Workbench, ido-static-recomp (https://github.com/decompals/ido-static-recomp).

### Inferences
- Directly transferable to ReverseApoc: per-function isolated agent workspace + CLAUDE.md/AGENTS.md, build-and-verify script with terse output, give-up rule, commit after each match, hooks protecting checksum files, similarity-based ordering, shared learnings file for compiler quirks (here Watcom).
- Nothing in these posts is x86/Watcom specific.

- Tools named: ARM ADS 1.2 (armasm/armlink/fromelf), pokefirered tools (gbafix, preproc), agbcc libs, GCC 13.2 for comparison, IDA, sha1sum, gbatek, Normmatt's gist of games built with ADS 1.2. — [post](https://abahbob.com/starting-a-decomp-project)

Definitions for README (author's synthesis; sources: awesome-decomp-games intro and PCGW page wording, and sm64/augustus READMEs above):
- **Reimplementation / engine remake** (OpenApoc, Augustus, OpenXcom): new code written to behave like the original, needs original data files; no requirement to match original code. OpenApoc itself: "open-source re-implementation of the original X-COM: Apocalypse, that requires the original files to run, GPL3, C++/SDL2, founded by PmProg July 2014" — [OpenApoc README](https://github.com/OpenApoc/OpenApoc).
- **Decompilation**: recovering readable source from the binary. **Matching decompilation**: source that, compiled with the original compiler and flags, reproduces the original binary byte-for-byte (verified by checksum). Awesome-decomp-games wording: "matching or functional" source-code reconstructions. Macabeus defines matching as writing readable C "that compiles to exactly the target assembly". — [Macabeus part 1](https://gambiconf.substack.com/p/development-journey-on-game-decompilation)

### Inferences

## OpenApoc Discord quote and the Win9x retail release question

### Takeaway
The quote cannot be fetched or verified; cite as an OpenApoc Discord message with link and the owner's handle/date. Sources confirm X-COM Apocalypse had a Windows listing dated same day as DOS (15 Jul 1997) with Windows 95 system requirements, but no source I found describes what a Win9x build changed.

### Cited Findings
- Quote to cite (supplied by owner, unverified by me, Discord not fetchable): "Yeah, IIRC the Win9x version is just an installer wrapper. Game beneath is identical and just uses DOS 7.x that's part of Win9x instead of DOS 6.2x that was the last packaged version of MS-DOS". Permalink: https://discord.com/channels/142798944970211328/691788237865353236/1560376052843413545 (server ID 142798944970211328 matches the OpenApoc Discord ID in the OpenApoc README badge). Suggested citation form: `> quote` then `-- <handle>, OpenApoc Discord, #<channel>, <date> ([message](permalink))`. Author handle, channel name and date unknown; owner to fill. Note it is hedged ("IIRC") and secondhand; label as recollection, not documentation. — [OpenApoc README Discord badge](https://github.com/OpenApoc/OpenApoc)
- PCGamingWiki lists release dates **DOS: July 15, 1997; Windows: July 15, 1997; Windows (DOSBox) (Steam): September 4, 2008**; system requirements OS minimum 5.0 / recommended 6.2 (DOS), RAM "8 MB (DOS), 16 MB (Windows 95)"; video SVGA; audio via Human Machine Interfaces (HMI) drivers; Smacker video; "Cutscenes remain on disk in the retail version". — [PCGW X-COM: Apocalypse (Wayback 2026-07-27)](https://www.pcgamingwiki.com/wiki/X-COM:_Apocalypse)
- Retail box requirements list identical CPU/disk/CD/video columns for MS-DOS 5.0, Windows 95 and Windows 3.1, with RAM 8MB (DOS) vs 16MB (Win95/3.1); the page has no installer notes. — [Eli's Software Encyclopedia](https://elisoftware.org/wiki/X-COM:_Apocalypse_(PC,_CD-ROM)_Microprose_-_1997_USA,_Canada_Release)
- 1997 demo readme says it also runs under Windows 95 with 16MB recommended (per search summary). — [search result summary, CD-ROM Today readme](https://discmaster.textfiles.com/view/1010/CD-ROM%20Today%20Volume%203%20n%C2%BA%209.iso/XCOM3/README.TXT)

- Wikipedia infobox lists DOS only (no separate Windows version); re-releases: X-COM Collection (Hasbro, 1999), Complete Pack (2K, 2008), 2K Huge Games Pack (2009), Steam from 5 Sept 2008 running in DOSBox. Wikipedia date: 15 July 1997 (NA); contradicts PCGW on the Windows platform listing. — [Wikipedia](https://en.wikipedia.org/wiki/X-COM:_Apocalypse), contradicted by [PCGW](https://www.pcgamingwiki.com/wiki/X-COM:_Apocalypse)

## 2026-10-25: jump tables and statics in `check` (Phase 6, plan 06-10, D-39)

- **A jump table that leads its function now passes `check`.** wcc386 10.6 puts a switch's table at `_TEXT+0`, before the function's public, and jumps through `jmp cs:[eax*4+_TEXT+0]` (05-REVIEW IN-02, observed again on a 6-case switch: six off32 entries at 0x0..0x14, the public at 0x18, no filler between). `check` pairs `[0, first public)` with the unit's data-in-code row right before the function's row, filler up to the function's row included, and checks that span like a function: equal length, equal bytes, and every table entry an off32 LE fixup to the original's case label. A wrong entry fails the function, naming the entry's VA. The real switch, laid into a synthetic LE built from its own object, passes; a planted wrong case target fails (`tests/test_check_tables_real.py`).
- **A table between two publics still fails closed, and now also when the layouts coincide.** An own public was sized to the next public, so a table after a public counted as part of that public's row: with our layout equal to the original's, the next function's `jmp` passed with its table never checked. Every own public is now no longer than its row, so that `jmp` is refused (`needs the unit's public-to-row map`). Most of the 80 UFO2P data-in-code rows are mid-unit tables of this kind; they wait for Phase 7.
- **A `static` named with its row's name passes, and so do its callers.** `static int func_XXXXXXXX(...)` is an LPUBDEF `func_XXXXXXXX_`, and a caller in the unit calls it through a plain EXTDEF of that name. omf2elf emits one LOCAL symbol of that name and no undefined duplicate (it skips an extern the module defines), so no ambiguous symbol reaches objdiff, and the relocation check resolves the call through the row. The probe with the real compiler showed this needed no code change; tests now pin it. A static with any other name (`helper`) still fails with the IN-01 message.
- **The pilot scorer keeps P16's exclusions until Phase 7.** `score` still skips a function with a jump table (any LE fixup inside its row that targets code), and the pilot's drafts stay non-static (D-09); Phase 7 admits both. Rules: [matching.md "Relocation rules"](matching.md#relocation-rules).

## 2026-10-24: what the Phase 5 code review turned up

- **A `static` function passes `check` only under its row's `func_` name.** wcc386 10.6 emits a `static` as an LPUBDEF under its own name, and a call to it, even inside the unit, as a self-relative fixup to an EXTDEF of that name. A static whose name is no row name (`static int helper(int)`) fails: the caller fails the relocation check (`unknown symbol`) and the unit fails its account. `check` names it: "a static (LPUBDEF) function, which check cannot pair with a row: give it its row's func_ name or keep the row INCLUDE_ASM" (static data likewise). Since 06-10 a static named `func_XXXXXXXX` after its row passes with its callers (2026-10-25 entry above).

## 2026-10-24: the first TACP match (Phase 5, plan 05-19)

- **func_00055080 of TACP.EXE matched on the first draft under the default rule.** It is `reverseapoc score tacp`'s candidate 1 (11 bytes: a call, a 32-bit store of its result, `ret`), far from TACP's uncovered stretch at 0x00029D4D..0x00031040, with no raw fields and no undecoded sites in its target cut. The unit u_00054f20 was kept as drafted. A mutation probe that declared the global `short` failed `check` (a 12-byte function, objdiff 98.3333%, relocation check failed, TACP splice refused), so the verdict is not vacuous.
- **The bytes cannot tell a `void` function from one that returns the stored value.** wcc386 does not save EAX in a `void` function that clobbers it, so `void f(void) { D = g(); }` and `int f(void) { return D = g(); }` give the same 11 bytes. The C says `void` until a caller that reads EAX after the call shows otherwise; the callers decide, not this function.
- **Two leaf-sized matches separate no candidate.** Neither has a loop, a branch, a struct copy or x87 code, so 10.5/10.6/11.0, `-4`/`-5` and `-o*` all stay tied. The `*` default and `__WATCOMC__` 1060 stay (D-18, D-14), and the cells that would settle each tie are listed under [toolchain.md "Flags"](toolchain.md#flags). The next matches should be chosen to carry a loop or a 5-dword struct copy, not only to be small.

## 2026-10-24: the first UFO2P match and the first real ninja graph (Phase 5, plan 05-18)

- **func_000A3980 matched on the first try under the default rule.** It is `reverseapoc score`'s candidate 1 (13 bytes: a call and a byte load returned as `int`). The one shape choice that mattered was the type of the global: the load sign-extends, so it is `extern signed char`, and plain `char` (unsigned under Watcom without `-j`) would zero-extend. A mutation probe that declared it `unsigned char` failed `check` (objdiff 46.7%, relocation check failed, 3 bytes differ, UFO2P splice refused), so the verdict is not vacuous. No sweep ran, so it proves the default rule for this function only and separates no compiler version or flag ([toolchain.md "Phase 5 match evidence"](toolchain.md#phase-5-match-evidence)).
- **The default `ninja` graph had never run on the real split.** With the committed CSVs, 18 of 842 target cuts failed: 13 rel32 branches and 3 off32 fixups pointed at code that no functions.csv row covers (split gaps, which D-11 leaves for later), and rt_i64tos in both EXEs decodes data as two branches out of the code object. The target writer now leaves such a field raw and names it in `raw_fields` (`off32 to no row`, `branch to no row`, `branch outside the code object`), as ruling F11 does for sel16. What the relocation check guarantees for such a function depends on the kind (corrected in 06-08, 05-REVIEW row 18a). `off32 to no row` always fails: rule 4 refuses a fixup of ours there because no name reaches a gap, and rule 5 refuses an object with none because the LE has a fixup there. `branch to no row` fails for every fixup of ours (rule 4), but a rel32 is no LE fixup, so rule 5 checks nothing and a displacement left unrelocated and byte-identical to the original passes. That this does not happen rests on wcc386 emitting a fixup for every call, even to a static. `branch outside the code object` can pass, because a data-object destination is nameable as `_D_<va>`. In both passing cases the landed bytes equal the original's and the whole-EXE SHA-1 gate holds, so the residual risk is bounded by byte identity; refusing such functions outright would be a stricter policy (the owner's call), not a correctness fix. tests/test_target.py pins all three kinds end to end. Rule: the docstring of `tools/reverseapoc/target.py`.
- **The compiler writes objects only inside the repository.** `reverseapoc cc` refuses an output under pytest's `tmp_path`, so the real compile tests write under `build/test-check/` (as `tests/test_compiler_real.py` uses `build/test-cc/`).

## 2026-10-23: Ghidra 12.1.4 headless with the LE loader (Phase 5, plans 05-03, 05-10, 05-12)

- **LeLoader needs `e_lfarlc == 0x40` or a BW chain.** The lastonesky loader takes `e_lfanew` only when the first MZ has `e_lfarlc == 0x40`, and otherwise walks "DOS/16 BW" headers; the real EXEs pass through the BW walk (a `BW` header at 0xF474), but the old test fixture's `e_lfarlc` (0xCCCC bound, 0x9090 unbound) and missing BW chain match neither, so the loader would refuse it (read from LeLoader.java's source, not run). Setting `e_lfarlc`/`e_lfanew` alone would also have moved every page by 0x180, because the data-pages field is then read relative to the first MZ; `build_le_image(ghidra_loadable=True)` in `tests/conftest.py` writes it that way. Rule: [toolchain.md "Ghidra and loaders"](toolchain.md#ghidra-and-loaders).
- **`analyzeHeadless` wants a project dir that already exists.** Without one it exits 1 with `Directory not found`, and it has no `-version` flag (it prints usage; read `Ghidra/application.properties` instead). `tools/reverseapoc/ghidra.py` creates a TemporaryDirectory before the run and passes `-deleteProject`.
- **The scripts are Java because Python is not available to Ghidra on 3.14.** Jython ships in 12.1.4 only as an uninstalled extension zip, and PyGhidra's bundled JPype wheels stop at cp313. The JDK compiles `tools/reverseapoc/ghidra_scripts/*.java` on the fly; both scripts ran unchanged on the first container run.
- **Ghidra's relocation table lists each page-straddling field twice.** Type 7 counts 28,197 = 28,183 + 14 (UFO2P) and 24,435 = 24,424 + 11 (TACP). Ghidra's bytes equal le.py's except at relocation sites, so bytes and fixups always come from `le.py`, never from Ghidra (P3, P4). Each export also holds one one-address "function" in the data object (UFO2P 0x0013BD40, TACP 0x002B405C), which reconcile drops. Rule: [toolchain.md "Ghidra and loaders"](toolchain.md#ghidra-and-loaders).

## 2026-10-23: capstone, raw off32 fields, splice and objdiff (Phase 5, spike 005, plans 05-03, 05-08, 05-09)

- **capstone's `__version__` is wrong.** `capstone.__version__` reports 5.0.7 for the 5.0.9 distribution; `importlib.metadata.version("capstone")` reports 5.0.9. `check_capstone()` in `tools/reverseapoc/x86.py` checks the pin through `importlib.metadata`. Rule: the capstone row of [tools.md](tools.md).
- **Raw off32 fields hold `target_off`, not the address.** wlink left the object-relative offset in every off32 field (52,607 fields: 28,183 in UFO2P, 24,424 in TACP), so decoding `load_flat(relocate=False)` gives tiny absolute operands. Operands over a fixup field are resolved through `le.fixups()` (`target_va`), discovery never reads a raw field as an address, and the target writer rewrites every field to its REL addend. Rule: [toolchain.md "objdiff and the OMF bridge"](toolchain.md#objdiff-and-the-omf-bridge).
- **splice masks LE fixup fields only.** A call rel32 field has no LE fixup, so splicing our raw bytes would write our placeholder displacement and break the SHA-1. `tools/reverseapoc/land.py` keeps the original bytes under every relocated field on either side, and only after the relocation check passed.
- **objdiff misses a wrong 2nd relocation of one instruction.** Spike 005's plant changed only the symbol of the imm32 in a `mov dword [abs32], imm32` and objdiff still scored 100.0; a wrong call symbol or addend scored below 100. The relocation check (`tools/reverseapoc/relocs.py`) plus the whole-EXE SHA-1 is the gate. Rule: [toolchain.md "objdiff and the OMF bridge"](toolchain.md#objdiff-and-the-omf-bridge); record: [spike 005](../.planning/spikes/005-objdiff-omf-elf/README.md).

## 2026-10-22: O_APPEND is not atomic on the bind mount or the Windows host (Phase 4 UAT gap G-04-2)

- **What happened.** 1600 parallel `cc` compiles all succeeded, but cc.log kept 72/80, 495/608 and 75/96 lines on the Docker Desktop 9p bind mount (/work, aname=drvfs, cache=0x5) and 732/736 on the Windows host; container-local /tmp kept 80/80. Lines were overwritten, not dropped: 9p and the UCRT (`_write` = `_lseeki64(FILE_END)` + `WriteFile`) emulate append as read-EOF-then-write, so two writers land on the same offset. A bare `0` line is the tail of a 519-character line under a 517-character one.
- **The fix.** `_append_log` holds an OS lock on `<log>.lock` across open, write and close. A release before the close still lost 102 and 118 of 1600 lines on 9p, because the bytes reach the server at close, not at flush. The blocking msvcrt modes retry once a second (13.5 s against 2.7 s per 1600 lines), so the Windows path spins on LK_NBLCK and treats only EACCES as busy. OS locks free themselves when the holder dies (0.003-0.011 s measured), so a killed `cc` never wedges the log; they do not cross the host/container boundary (the host lost 222/1200 lines with both writing). Rule: [toolchain.md "wibo"](toolchain.md#wibo).
- **The test lesson.** A concurrency test under tmp_path passes in the container even with the bug, because overlay fs appends atomically. `tests/test_cc_log.py` writes under build/, so the container run exercises the bind mount.

## 2026-10-21: what the Phase 4 code review turned up

- **10.5 writes no error file.** With `-fr=<file>`, 10.6 and 11.0 write the error file next to the object; 10.5 (the BINNT stub running the decoded BINW compiler) writes none anywhere, and the message still reaches the captured output. Found once the wrapper's invariant tests ran for 10.5 too (review WR-05); `tests/test_compiler_real.py` records it.
- **`-zld` empties the dependency list but keeps its end marker.** Counting COMENT classes (no bytes) in objects of a plain and a header-including source: without `-zld` each object has one COMENT 0xE9 per file (source, then headers) plus an empty one; with `-zld` only the empty 0xE9 remains, on 10.5, 10.6 and 11.0. So the wrapper's objects carry no dependency paths or timestamps, and of the two host-specific records only THEADR still names a path; the normalized hash still drops 0xE9, which matters for objects built without `-zld` (review IN-01).

## 2026-10-21: running the 1990s compilers (Phase 4, plans 04-01..04-06, 04-11)

- **wpack needs Watcom's own qsort.** The 10.5 compiler's archive (PCK00017.1 + .2) builds its Shannon-Fano code table with the Watcom C library's qsort (shell sort below 16 items, Bentley-McIlroy partition above). A stable sort assigns tied symbols in another order and decodes garbage ("a match runs past the member length"). The 10.5 header is 12 bytes (the first member's `disk_addr` is 12); Open Watcom v2's 16-byte variant is refused. Format: [research/wpack-format.md](research/wpack-format.md).
- **The BINW compilers of 10.5, 10.6 and 11.0 are all LX images, not LE.** `BINW/WCC386.EXE` (567,558 bytes in 10.5, decoded; 567,698 in 10.6; 653,342 in 11.0) has `LX` at `e_lfanew` 0xE38 in each, and `uv run reverseapoc parse-le` rejects them ("no LE header found"). `config/watcom.toml`'s 10.5 and 10.6 BINNT notes still say "the real LE compiler"; those notes are stale for both versions (all three BINW compilers are LX), and the manifest is protected, so they stay until the owner edits it. Correction, 2026-10-21: this entry first called the 10.6 compiler LE; reading its `e_lfanew` shows LX.
- **The 10.x BINNT loader finds BINW by itself.** It reads its own path (`GetModuleFileNameA`) and opens `..\BINW\WCC386.EXE`; PATH, `WATCOM` and DOS4GW are not needed. This replaces the "to be confirmed in Phase 4" in the 2026-10-19 entry below. Rule: [toolchain.md "What is on the discs"](toolchain.md#what-is-on-the-discs).
- **The compiler reads options from the environment.** `WCC386=-3r` turned `and eax,0FFh` into `movzx` on 10.6 and 11.0; `INCLUDE` changes the header search, and compose loads `.env` into the container. The wrapper builds the child environment from scratch. Rule: [matching.md "Pitfalls"](matching.md#pitfalls).
- **NT-hosted compilers target NT.** Without `-bt=dos`, `__NT__` is defined and the headers and default libraries change. The wrapper always passes `-bt=dos`.
- **Objects carry absolute paths, so compare the normalized hash.** THEADR holds the absolute source path and COMENT class 0xE9 absolute header paths and timestamps, even for a relative command line. Raw SHA-1s never agree across host and container; the SHA-1 without those records was equal native vs wibo for 10.5, 10.6 and 11.0 (D-03, spike 004). Rule: [toolchain.md "wibo"](toolchain.md#wibo).

## 2026-10-21: what the game-code scan says, and what it cannot say (Phase 4, plans 04-08..04-11)

- **mosura's register claim did not reproduce.** On our clean-room counted loop, 10.6 kept the bound in `ecx` and 11.0 in `ebx`, the opposite of the published table. Register choice is construct-specific; every idiom is now calibrated per version and flag set from our own probe. Rule: [matching.md "Known idioms"](matching.md#known-idioms).
- **The research's adjacent `B9 n 00 00 00 F3 A5` pattern could not see a `-4` struct copy.** The probe's own `-4r` copy has register moves between `mov ecx,5` and `rep movsd`, so the research's "0 hits, so no `-4`" never ruled `-4` out. The corrected counter, and then a sized count of every rep copy (04-10 review), found 5-dword rep copies in both EXEs (UFO2P 2 plus about 2 the recogniser skips, TACP 6 plus 2) and no unrolled 5-dword run. Only the 5-dword size separates `-4` from `-5`. Result: `-4r`, recorded in [toolchain.md "Flags"](toolchain.md#flags).
- **The switch-order counter had a defect, and switch order is not a version signal.** A compare that turned the direction dropped the chain before it, and chains crossed function boundaries; that made 11.0 `-ox` look descending. Fixed (04-08 review): every cell except `-oneatx` (none) has one ascending chain on both versions. The compare forms still cover only `eax`/`al`.
- **"No 11.0, no `-4r`" did not hold.** With the corrected counters, 11.0 `-4r` stays consistent with both EXEs, and so do 10.5/10.6 at `-4r` and `-5r`. 10.5 and 10.6 are byte-identical on all ten probe flag sets. The decisive idioms leave 10.6 and 11.0 tied at `-4r`; the first Phase 5 matches decide. Recorded as a tie in [toolchain.md "Result"](toolchain.md#result).
- **Stack checks are off for most code.** 40 (UFO2P) and 32 (TACP) `push imm32; call __CHK` sites sit in two 64 KiB blocks. A throwaway count (not a committed command) found at least 714 / 801 near-call targets in non-library code that two or more call sites reach, so `-s` is the default and the `__CHK` functions are exceptions for per-glob rules.
- **Library stubs fake the C++ runtime.** At a 16-byte threshold, CLIB's 18-byte `noefgfmt`/`nomem` stubs match the C++ `__wcpp_` undefined-member stubs, and C++ `fatalerr` matches the head of CLIB's `__fatal_runtime_error_`. Only exclusive, consistent C++ matches count; none remain, and `cppscan` says `C (wcc386): ...` for both EXEs. Rule: [matching.md "Pitfalls"](matching.md#pitfalls).

## 2026-10-20: ninja quotes $in, nothing else (Phase 3 review WR-05, WR-06)

- **ninja already shell-quotes `$in` and `$out`** (single quotes on POSIX, double quotes on Windows only where needed), so quoting them in a rule double-quotes them. `configure.py` keeps `parse-le $in` unquoted, and a test pins the rule line.
- **Literal text in a rule command reaches /bin/sh or CreateProcess as written**, so `configure.py` accepts only letters, digits and `. _ - / :` in the `--orig` path it writes. ninja 1.11.1 has no escape for `|`, LF or CR in a build path, so `configure.py` refuses such executable names with an error instead of writing a broken `build.ninja`.

## 2026-10-20: refactors need their own review (PR #1, Python tooling)

- **Flattening changed behaviour twice.** In the `code-simplifier` refactor of the ISO9660 walk, a lazy generator became a list, so `find()` failed on a bad record that came after the match. In the `fetch_media` refactor, a Content-Length refusal started deleting an older `.part` file. Both were caught by a `/code-review` run after the refactor, not by the existing tests, and both are now pinned by tests.
- **Characterize first, then prove the tests bite.** Before moving code, add tests for the behaviour being moved, then break the code briefly to watch each one fail. Two tests written this way (the associated-file skip and directory-named errors) had no coverage before.
- **Named offsets read better than comments.** The bare `25`, `32`, `33` and `34` in the ISO reader became constants named after their ECMA-119 fields. The rules now live in [coding-style.md](coding-style.md#python-tooling).

## 2026-10-19: what is actually on the Watcom CDs

- **BINNT is a stub on 10.5 and 10.6.** `BINNT/WCC386.EXE` is a 9,216-byte Win32 loader that tells you to put `BINW` in your path first; the real compiler is the LX image `BINW/WCC386.EXE` (567,698 bytes in 10.6; not LE, see the 2026-10-21 entry above). Running 10.x under wibo needs `BINW` next to `BINNT` (to be confirmed in Phase 4). 11.0 and later ship a native Win32 `BINNT`.
- **The 10.5 disc has a damaged compiler.** `BINW/WCC386.EXE` is a 65,536-byte stub; the real 567,558-byte binary is wpack-packed in `DISKIMGS/DISK02/PCK00017.1` + `DISK03/PCK00017.2`. `check-watcom` reports it as KNOWN BAD; decoding is Phase 4 work.
- **The 11.0b dump has a damaged directory sector (353)** covering the 3-file `SAMPLES/WIN/DATACTL/WIN16` folder. 7-Zip cannot open the image; our reader installs it and skips that folder (manifest `skip_dirs`). The compiler, headers and libraries are fine.
- **The archive.org and WinWorld copies are byte-identical** (10.5, 10.6, 11.0), so the collection item's SHA256SUMS and cross-verification notes corroborate our SHA-1s in `config/watcom.toml`.

## 2026-10-19: kickoff research outcome

- **Targets are clean and fixed.** Steam and GOG ship byte-identical UFO2P.EXE (`ufo24`) and TACP.EXE (`tac4`): Watcom LE executables bound with DOS/4GW Professional, two objects each, no debug info, almost certainly C rather than C++. OpenApoc expects a different UFO2P build (CRC32 `0x4749ffc1` vs our `0xDBD3B41D`): resolved the same day, see below.
- **The compiler hypothesis is Watcom 10.6 (10.5 equivalent).** The runtime banner excludes only 10.0/10.0a; codegen idioms point away from Open Watcom, which cannot match. 11.0 is told apart by a codegen probe. Phase 4 settles it with owner-supplied compilers.
- **objdiff cannot read Watcom OMF.** Theme Hospital's GPLv3 `omf2elf.py` is the bridge, which is why `tools/` is GPLv3. Whether objdiff diffs converted objects cleanly decides hybrid vs fallback in Phase 5.
- **Pipeline is hybrid.** Our own oracle (KKND's LE reader and in-place splice, Theme Hospital's build pattern, wibo + Docker) plus decomp.wtf's fork mode as the agent layer. decomp.wtf was archived and decomp.dev closed in October 2026, both citing AI-driven behaviour, so we state AI use openly and self-host progress.
- **The driver, not the agent, owns verification.** Successful AI decomps (Lewis, Macabeus) stood on deterministic verifiers; agents that could judge themselves claimed false matches and edited hashes. Hence a 3-5 attempt cap with re-queue, hooks on hashes and build scripts, and a driver that re-checks bytes before every commit.

## 2026-10-19: the OpenApoc CRC mismatch is two builds on the same disc

- **What we found.** OpenApoc reads `ufo2p.exe` from the CD image, and the Steam `cd.iso` / GOG `XCOM.BIN` carry the v1.00 CD build (UFO2P.EXE 1,702,206 bytes, CRC32 `0x4749FFC1`; TACP.EXE 3,170,298 bytes). The installed `XCOMA/` tree holds a second build (1,705,790 / 3,161,594 bytes) that is also on the disc, as `XCOM3/UFOEXE/UFO2P4.EXE` and `XCOM3/TACEXE/TACP4.EXE` (byte-identical; trailer spike 003, 2026-10-20), so it is not a store patch. Verified with pycdlib on both disc images; SMKP.EXE and XCOMAPOC.EXE are identical in both.
- **Why it matters.** OpenApoc's offsets and `FUN_` addresses only apply to the CD build. We keep the installed build as primary target, record the CD build in `config/targets.toml`, and treat the build-to-build diff as free matching evidence later. Which build is newer is unknown; a build-to-build diff after Phase 5 may tell.

Worktree note: the 10.5 ISO lives in the main checkout's gitignored third_party/watcom-media/. Real tests read it
through `REVERSEAPOC_WATCOM_MEDIA="$(git rev-parse --path-format=absolute --git-common-dir)/../third_party/watcom-media"`,
in memory and read-only. A real-file test that skips with that override set is a failure. No compiler bytes are
ever printed, logged, committed or embedded; sizes and hashes only.

What research measured (04-RESEARCH.md "Pattern 1: wpack decoder", Pitfall 8, prototype in a scratchpad that is NOT
in the repo): parts are a plain concatenation (109,568 + 247,871 = 357,439 bytes = info_offset 357,412 + info_len
27); the header on this disc is 12 bytes (u16 signature 0x2403, u8 major 1, u8 minor 1, u16 num_files, u16
info_len, u32 info_offset), not Open Watcom v2's 16-byte struct, and the first member's disk_addr is 12; file_info
is u32 length, u32 disk_addr, u32 stamp, u32 crc, u8 namelen (bit 0x80 = NO_SHANNON), name; the CRC is standard
CRC-32 (zlib.crc32) of the compressed bytes [disk_addr, next member or info_offset); decoding is LZSS (window
4096, lookahead 60, threshold 2, window pre-filled with spaces, start position 4096-60) with 314 literal/length
symbols coded by a static canonical Shannon-Fano code whose code-length table is run-length packed; positions use
the LZHUF d_code/d_len tables (6 high bits table-coded, 6 low bits raw); NO_SHANNON streams use a 1-bit flag plus
an 8-bit literal or a 6-bit length plus position. The symbol order for equal code lengths comes from Watcom's
CLIB qsort (shell sort for n < 16, Bentley-McIlroy 3-way partition with median-of-3 / pseudo-median-of-9 above);
Python's stable sorted() produced garbage with no MZ, a faithful port produced a valid file.

<objective>
Close gap G-04-2 (UAT test 2, owner: "issue: the log loss."). In the UAT, 1600 parallel `reverseapoc cc` compiles
all succeeded, but cc.log lost and tore lines on the Docker Desktop 9p bind mount and on the Windows host. The
log is the provenance record of which compiler@version and flags built each object (CID-01: each compiler
binary's hash and banner are logged), so a lost line is a lost record.

Root cause (diagnosis, confirmed): stale-offset overwrite, not dropped writes. `_append_log` does an
unsynchronised `open("a")` + write and relies on O_APPEND being atomic between processes. On the 9p drvfs mount
(cache=0x5, writeback) and in the Windows UCRT, append is emulated in two steps: read EOF, then write at that
offset. Two writers that read the same EOF overwrite each other. Container-local fs is correct.

Fix (design A of the diagnosis, recommended and measured): serialise read-EOF -> write -> CLOSE across processes
with a stdlib OS lock on a sidecar `<log>.lock`, taken before the open and released after the close.

Purpose: Phase 5's `ninja -j` runs many `cc` at once. Without this fix, the log silently loses which compiler
built which object.
Output:
- the lock in tools/reverseapoc/compiler.py, with the tests written first and shown red on the host and in the
  container before the fix;
- five reverted mutants proving the tests bite;
- docs in toolchain.md and learnings.md;
- the done gate on host and container, logged under build/gate/04-13/ and reproduced in the SUMMARY.

- Platform helpers, defined per branch, with shallow nesting:
  - POSIX: `_acquire(fh)` runs fcntl.flock(fh.fileno(), fcntl.LOCK_EX), and `_release(fh)` runs LOCK_UN.

    contention errno the non-blocking mode sets) and re-raises every other error.
  - `_acquire(fh)` runs fh.seek(0), then loops `while not _try_lock(...)` with time.sleep(_LOCK_RETRY_SECONDS).
  - `_release(fh)` runs fh.seek(0), then msvcrt.locking(fd, msvcrt.LK_UNLCK, 1).
  - Use only the non-blocking msvcrt mode; the blocking modes retry once per second.
- `_log_lock(log: Path) -> Iterator[None]`, a contextmanager:
  - It opens _lock_path(log) in "a+b". That creates the file if needed and never truncates or writes it.
  - It acquires the lock, yields, and releases in a finally block. The `with open` closes the lock file.
  - The sidecar is never deleted: deleting would reopen a create/delete race, and a dead holder leaves nothing to
    clean up, because the OS lock dies with the process.

## Summary

The review covers plan 07.1-02's `tools/` and `tests/` changes from `f0be9878` to `e18354ec`: `slots.py` and its two test files are new, and `search.py`, `cli.py` and `tests/test_search.py` were extended. For `search.py` and `cli.py` the review read the plan's diff and every helper it calls, including `batch.slot_map`, `_frame_slots`, `function_slots` and `function_body`. `probe/cg_slots.c` was read only to learn what was measured, and the YAGNI lens does not apply to it.

No finding is a blocker. Nothing here can make a wrong match land, because `exact` is still `check`'s verdict and only the gate claims a match. The specific severity rubric files logic errors as warnings, and these are logic errors in a tool that ranks and suggests. They are not minor, though: WR-01 and WR-02 make the search drop the one move that fixes a function, and WR-01 also tells the operator that move cannot exist.

The main concerns:

- **"Scalar" means more than the model measured (WR-01).** Plain `float`, `double` and `volatile` locals sit in the frame like memory locals, and declaration order moves them. The search treats them as register candidates, computes no move and prints `declaration moves cannot reach them`. Proved in both calibrated cells, and a committed function (`src/tacp/u_00098010.c`, `func_00098300`) has this shape.
- **A `None` from the inverse empties the axis (WR-02).** Plan 1's moves are given up as soon as the shape is computable, even when the slot map is too thin to support the answer. The map of a non-exact function is often partial, and a non-exact function is what the search exists for.
- **The computed path has never run on a real map in the suite (WR-08).** `test_search_real.py` takes the fallback, as the SUMMARY says, so WR-01 and WR-02 stayed invisible.

What held up under attack, so nobody needs to re-check it:

- `order_is_known`'s single-size rule held on the real compiler, in both cells, well past the probe's counts: 13 `int`s, 10 `short`s and 10 `char`s.
- It also held for ties of one size but mixed type (`int` with `char[4]`, `int[1]`, a pointer or a `float`; `short` with `char[2]`; `char` with `char[1]`), for an `int` tie beside spills up to 5 locals, and for 10 ints over 5 sibling blocks. The mixed-type ties beside an `int` were read under `-oneatx` only for four shapes, because `-4r -s` merged their tails.
- Distinct sizes across blocks follow M1.
- `declaration_order`, `_ordered` and `_declaration_move` traced clean, and on a full real map the axis produced the right order in both cells.
- The `_axis_moves` wiring, a base that fails to compile (`function_body` returns its key and the map comes out empty), `_best_cell` and the `cli.py` line are sound.

Each claim marked "proved" was run. Compiler claims used the real wcc386 10.6 on scratch C, with objects under a temporary `build/` directory that was removed afterwards; the drive lock was free. The other proved claims were run against the real modules from a script outside the repo. The full suites were not run for this review.

**How often the computed path applies (the SUMMARY left this uncounted).** Over the committed `src/`, a regex scan found 109 function definitions, 36 of them with declared locals. Of those, 27 reach the computed path given a map: 26 with no memory local, so the axis is always empty, and 1 with a single memory local, so there is nothing to order. None has a tie to compute. Committed C is matched code and only a proxy for lifter drafts, but on it `_target`, `slots.declaration_order` and `_ordered` have nothing to do, and the only effect of the plan's wiring is the skip.

YAGNI lens: `reverseapoc search` gained no option, and `cli.py` gained only the `scalars:` line the plan asks for. There is no single-implementation abstraction. The computed path is not a YAGNI break even with the count above, because the plan requires it. Two small breaks are recorded, IN-01 and IN-02.

## Warnings

### WR-01: Plain `float`, `double` and `volatile` locals are read as scalars, so the axis is skipped and the output is false

**File:** `tools/reverseapoc/search.py:409-421` (also `:475-483`, `tools/reverseapoc/slots.py:13-17`, `:47-55`, `:98-108`)
**Issue:** `_readable` accepts any local of 4 bytes or more outside `memory`, on the grounds that M5 puts it out of reach of declarations. M5 was measured on `int` and `short` only: no `pr_spill_*` shape holds a `float` or a `double`, and `cg_slots.c`'s doubles are all address-taken. Proved on wcc386 10.6, identical under `-4r -s -fpi` and `-4r -oneatx -s -fpi`:

- `int a; int b; double p;` against its declaration twin `double p; int a; int b;`: the real map holds `(0x8, 0xc)` and `(0xc, 0x8)`, frame 0x10 on both sides. `_computable` is True, the axis yields 0 moves (plan 1 had 603), and `_scalars` returns `(0x8, 0xc)`. Those are the two address-taken ints, and the fix is a declaration move, yet the verb prints `declaration moves cannot reach them`.
- `float p; float q; float r;` against its reverse: the bodies differ, `memory_locals` is empty, `_computable` is True, the axis yields 0 moves, and `_scalars` returns `(0x0, 0x8)`. The same shape in `double` returns `(0x0, 0x10)`. This disproves "declarations cannot reach them" for these types directly.
- `int a; int b; float f;`: the float takes slot 0 and the ints sit at 8 and 4, where `frame_layout` says 4 and 0.
- `double d; int b; int a;`: measured `b` 8, `a` 0xC, the opposite of M2. `order_is_known` still says True, because it never sees `d`. This is `pr_tie_small` again, through a local the model cannot see.
- `int a; volatile int v; int b;`: frame 0xC, `a` at 8, `b` at 0. `_QUALIFIERS` strips `volatile` and `_in_frame` calls `v` a register candidate.

Reach: `func_00098300` in `src/tacp/u_00098010.c` holds plain `float w` and `float sum`, and it passes `_readable`.
**Fix:** Only an integer or a pointer of a slot or more can stand outside `memory`, and every other frame falls back:

```python
_FRAME_TYPES = frozenset(("float", "double"))  # plain ones still take a frame slot

def _scalar_candidate(found: re.Match[str], size: int) -> bool:
    """A local outside the memory locals that M5 covers: pr_spill_* measured integers only."""
    words = found["spec"].split()
    pointer = "*" in found["declarators"].split("=")[0]
    return (size >= slots.SLOT_ALIGN and "volatile" not in words
            and (pointer or words[-1] not in _FRAME_TYPES))
```

`_readable` then requires `name in held or _scalar_candidate(one, size)` for each local. Add the `double`, `float` and `volatile` shapes to `probe/cg_slots.c` with their twins, and say in `slots.py`'s M5 that it covers integers and pointers.

### WR-02: A slot map that cannot support the inverse empties the axis instead of falling back

**File:** `tools/reverseapoc/search.py:424-445`, `:461-472`
**Issue:** `_computable` never asks whether the map places the locals. `_target` then fills the gaps ("a local the map does not show stays where it is") and takes `moved[0]` from whatever pairs exist. `declaration_order` returns None, or the identity, and `declaration_axis` yields nothing, with plan 1's moves already given up. Four routes:

- **Partial map, proved in both cells.** Ours `int a; int b; int c;`, theirs `int b; int c; int a;`, with the bodies differing so that the matcher cannot align `c` as well: the real map is `((0x4, 0x8), (0x8, 0x0))`. `c` stays at 0, the target holds 0 twice, `declaration_order` returns None, and the axis yields 0 moves against plan 1's 603. The answer is one declaration move away, since the third offset follows from the other two.
- **Conflicting map, proved.** `SlotMap(((0, 0), (0, 8), (4, 4), (8, 0)), False, 0xC, 0xC)` gives 0 moves. `batch.slot_map` documents such conflicts, and `SlotMap.bijection` exists to report them, but nothing here reads it. The real `float` maps of WR-01 are non-bijective too.
- **Another coordinate system, proved.** `_slot` returns a negative `[ebp - N]` displacement in an ebp-framed body. A map of `((0, -4), (4, -8))` gives 0 moves. With `ours` negative every local reads as not shown, so the axis reports nothing to move. The 07.1-01 review counted 84 rows with `[ebp - N]` locals.
- **Spills only in theirs, proved.** `fits` checks `frame_ours` alone. With `short b; short d;`, `SlotMap(((0, 0xC), (4, 8)), True, 8, 0x10)` gives 0 moves. Theirs has the spills, and spills do push shorts up the frame (measured: `short` ties beside 8 spills sit at the top). Having fewer spills than the original is the usual state of a non-exact function.

**Fix:** Compute only from a map that places every memory local, and leave the rest to plan 1's moves. `test_declaration_axis_yields_nothing_when_size_rules_the_target_out` stays valid, because its map shows both locals.

```python
def _places_all(memory: Sequence[slots.Local], slot_map: batch.SlotMap) -> bool:
    """The map shows every local of `memory`, each moved one way and still inside the frame."""
    layout = slots.frame_layout(memory)
    for local in memory:
        start = layout[local.name]
        moved = {theirs - ours for ours, theirs in slot_map.pairs
                 if start <= ours < start + local.size}  # fmt: skip
        if len(moved) != 1 or start + min(moved) < 0:
            return False
    return True
```

Add this to `_computable` after `order_is_known`, and make `fits` require `frame_theirs` as well as `frame_ours`. This check was run on the partial, conflicting and both ebp maps above: it returns False for each, and True for the full map. With an empty `memory` it returns True, so the scalar skip is unchanged, and pairs outside every local, such as a shifted negative slot, do not count against it.

### WR-03: `&p->x` and `&p[i]` put a plain pointer in `memory_locals`

**File:** `tools/reverseapoc/search.py:386`
**Issue:** `_in_frame` stops at `&\s*{name}\b` and never looks past the name, so taking the address of what a pointer points at reads as taking the address of the pointer. Proved: `struct pos *p; ... take(&p->y, &a, &b);` compiles with a frame of 8, `a` at 4, `b` at 0, and `p` in a register, in both cells. Yet `memory_locals` lists `p`, as it does for `int *p; take(&p[1]);`. The model then places a local that has no slot. With `int b; int c; struct pos *p;` and a real swap of `b` and `c` (`(0, 4), (4, 0)`), the axis offers `int b; struct pos *p; int c;`, which swaps `c` with `p` and leaves the frame unchanged. The wrong layout also shifts `bottom` in `scalar_slots` by 4. `test_a_unary_and_takes_the_address` pins `&b.x` but neither of these forms.

Reach: none in the committed C, where a recount through this regex finds no such pointer. Lifter drafts can still hold it, since `&p->field` is ordinary C.
**Fix:** Refuse a following `->` or `[`. An array needs no such match, because the second branch of `_in_frame` holds it.

```python
if re.search(rf"{_BEFORE_ADDRESS}\s*&\s*{name}\b(?!\s*(?:->|\[))", body) is not None:
```

### WR-04: `_BEFORE_ADDRESS` misreads `&` in both directions

**File:** `tools/reverseapoc/search.py:88-91`
**Issue:** Proved through `memory_locals` on `int b;`:

- False positives, where `b` is listed as held in memory: `b = a++ & b;` (`a-- & b` takes the same path through the `-` in the class), `b = sizeof(int) & b;`, and `b = 'a' & b;`, where the blanked literal leaves `=` before the `&`.
- False negatives, where the local is missing: `take((DWORD)&b);`, since only the types in `_SIZES` count as a cast, and `take(a && &b);`, since `&` is not in the class.

A false negative is the worse one: the address-taken local is absent from `memory`, `_readable` passes because its size is 4 or more, and the computed layout misses a slot. The comment at `:88` claims a complete rule: "Anything else leaves a binary `&`".
**Fix:** Exclude a postfix `++` or `--` with a lookbehind, add `&&` to the alternatives, and match `sizeof` before a cast. A bare `(Name)&b` cannot be told from `(a) & b` without types, and `test_a_bitwise_and_takes_no_address` pins that spelling as binary. So have `_readable` refuse a frame where `(identifier) & local` appears: an ambiguous read then falls back.

### WR-05: An address-taken parameter or an initialized array stays on the computed path with a wrong layout

**File:** `tools/reverseapoc/search.py:393-421`
**Issue:** The SUMMARY's "Seen, not built" records both as limits of the model, but the effect is not a missing feature. `_readable` promises that "every local has a size", and these occupants pass it unseen, so the axis computes from a wrong frame instead of falling back. Proved:

- `void f(int x) { int a; int b; ... pr_take(&a, &b, &x); }` under `-4r -oneatx -s -fpi`: frame 0xC, `a` at 8, `b` at 4, against the model's 4 and 0. `-oneatx` is the search cell.
- `int v[2] = {0x555, 0x666}; int a; int b;`, both cells: frame 0x10, `a` at 8, `b` at 0xC. The model has 4 and 0, so both the base and the order are wrong (the `pr_tie_small` flip). `_DECLARATION` excludes `{`, so `memory_locals` leaves `v` out.

**Fix:** Refuse in `_readable`: return False when the body takes the address of a parameter, and when a line in `span` holds `=` followed by `{`. Both tests are a few lines on the blanked code, and neither adds a model rule.

### WR-06: A slot with two targets is printed twice

**File:** `tools/reverseapoc/search.py:482`, `tools/reverseapoc/slots.py:108`
**Issue:** `SlotMap.pairs` can hold one `ours` slot with two `theirs`, which is the conflict `bijection` reports. `_scalars` keeps one entry per pair and `scalar_slots` only sorts. Proved: `scalar_slots((Local("b", 4),), [8, 8], 0x10)` returns `(8, 8)`, so the verb prints `scalars: slots 0x8, 0x8`.
**Fix:** `return tuple(sorted({offset for offset in mismatched if bottom <= offset < top}))`, with a case in `tests/test_slots.py`.

### WR-07: An octal array dimension is read as decimal

**File:** `tools/reverseapoc/search.py:376-378`
**Issue:** `"010".isdecimal()` is True and `int("010")` is 10, so `int v[010];` reads as 40 bytes where C gives 32. Proved through `memory_locals`. `_size` promises None for a size that is not a plain number, and a wrong size is worse than none, as `frame_layout`'s own docstring says. The reach is small, since lifter output has no reason to write octal.
**Fix:** Accept `re.fullmatch(r"[1-9]\d*", text.strip())` in place of `isdecimal()`, so the octal form falls back like `[0x10]`.

### WR-08: The computed path has no test on a real slot map

**File:** `tests/test_search.py:1154-1358`, `tests/test_slots_real.py`
**Issue:** Every computed-path test in `test_search.py` hands `declaration_axis` a hand-written `SlotMap`. `tests/test_slots_real.py` holds `frame_layout` against the compiler but never calls `batch.slot_map` or `declaration_axis`. `tests/test_search_real.py` has one test, and the SUMMARY records that it passes through the fallback. So the claim that the search computes the order the original's slots need, must-have truth 4, is unproved on real input. WR-01 and WR-02 show what stubbed maps hide: real maps are partial and non-bijective, and stubbed ones are tidy.
**Fix:** Add a test to `tests/test_slots_real.py` that needs no EXE: compile two clean-room functions that differ only in declaration order, call `batch.slot_map(ours, theirs, 0, set())`, and assert that `declaration_axis` yields the other text. This review ran that with `int a; int b; int c;` against `int b; int c; int a;`: the map came out `(0, 4), (4, 8), (8, 0)` and the axis gave the right order in both cells. Add the WR-01 and WR-02 shapes alongside it as cases that must fall back.

## Info

### IN-01: YAGNI: `scalar_slots` takes an `Iterable` for a caller that does not exist

**File:** `tools/reverseapoc/slots.py:98-105`
**Issue:** The later-use code is the `locals_: Iterable[Local]` parameter and the `locals_ = tuple(locals_)` copy it forces. The only callers pass a tuple. `frame_size` does need `Iterable`, because `scalar_slots` hands it generators.
**Fix:** Type it `Sequence[Local]`, as `frame_layout` is, and drop the copy.

### IN-02: YAGNI: `_CAST` is sorted for an alternation where order cannot matter

**File:** `tools/reverseapoc/search.py:90`
**Issue:** The later-use code is `sorted(_SIZES, key=len, reverse=True)`. Longest-first matters when an alternation can stop early, but here `\s*\)` follows it, so backtracking reaches the same match in any order.
**Fix:** `"|".join(re.escape(spec) for spec in _SIZES)`.

### IN-03: Two predicates answer "is this local in memory" differently

**File:** `tools/reverseapoc/search.py:319-325`, `:381-390`
**Issue:** `_in_memory` (plan 1) counts a bitwise `&`, every aggregate and any unread type. `_in_frame` (this plan) means something stricter, under nearly the same name and docstring. The next reader can easily take one for the other.
**Fix:** Rename `_in_memory` for what it does (for example `_moves_first`, since it only orders the pairs), or say in its docstring that `_in_frame` is the one the model trusts.

### IN-04: The module docstring names two fallback reasons, and the code has six

**File:** `tools/reverseapoc/search.py:19-22`
**Issue:** It says the plain moves stand "because a size is unknown or a tie has no known order". `_computable` also falls back on an empty map, a repeated name, a plain local under 4 bytes and a small local beside spills. The SUMMARY lists most of these, but the code's own account is short of them.
**Fix:** Point the sentence at `_computable` instead of enumerating, so it cannot go stale again after WR-01, WR-02 and WR-05.

### IN-05: `_stores` keeps register constants across calls

**File:** `tests/test_slots_real.py:147-165`
**Issue:** `constants` is only written by `mov reg, imm`. A `call`, or any other write to the register, leaves a stale value, so `mov eax, 0x11` followed by `call pr_get` and `mov [esp + N], eax` yields `(0x11, N)`, and `dict(...)` keeps the last store. This has not bitten: the shapes pass. It would surface as a false failure on the next shape that routes a marker through `eax`.
**Fix:** Clear `constants` on `insn.is_call`.

### IN-06: The model runs on committed cells outside its stated calibration

**File:** `tools/reverseapoc/slots.py:2-4`, `tools/reverseapoc/search.py:585-595`
**Issue:** The docstring scopes the model to two cells, but `_axis_moves` applies it to whichever cell ranks best, and `config/cflags.txt` has 5 rules under `-4r -ot -s -fpi` and `-4r -ox -s -fpi`. No defect was found. All 21 `SHAPES` and both `SAME_CODE` pairs hold in those two cells, proved on the real compiler. One difference: `pr_spill_short` and its twin come out identical under `-ox`, so the M5 exception does not show there. The stated scope and the code still disagree.
**Fix:** Add both cells to `CELLS` in `tests/test_slots_real.py` so the suite holds what this review measured, and update the docstring to match. D-02 is kept: this is still only `probe/` C.

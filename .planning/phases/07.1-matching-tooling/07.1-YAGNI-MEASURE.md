# Phase 7.1: does the YAGNI rule pay off?

Written 2026-11-03, before any Phase 7.1 execution. **This file is frozen: it is committed once and
never edited.** Per-plan numbers go in `07.1-YAGNI-RESULTS.md`, and the curve in `07.1-CURVE.md`.

The question: does the "YAGNI: scope, not effort" section of `.claude/rules/tools.md` make tooling
plans smaller or cheaper, without weakening tests, review results or what the tools deliver? This
compares 7.1's plans with the closest earlier tooling plans, written without the rule.

Real trains vary by about ±25% per plan, and the plans differ in what they build. **Every result here
is indicative, not proof.**

## What each plan records

| Symbol | Meaning | How |
|---|---|---|
| `L` | Production lines added under `tools/`, tests apart | `git diff --numstat` from `plan_head_before` to the train's last commit, review fixes included |
| `T` | Test functions added | `def test_` lines added under `tests/` |
| `M` | `must_haves.truths` in the PLAN frontmatter | Counted from the plan as written; fixed before execution. It normalizes plan size |
| `E` | Effective tokens for the whole train: main session plus every subagent | input×1 + cache read×0.10 + cache write×1.25 + output×5, one count per `message.id` |
| `US$` | E × the model's input rate per token | Rate and its date recorded with the row |
| `F` | Review findings by severity | CR, BL, WR, IN from the plan's review |
| `Y` | YAGNI `IN-` findings | An unrequested option or flag, a single-implementation abstraction, code written for later |
| `D` | Defects found after the plan closed | `fix` commits or findings on that plan's code, up to the earlier of 14 days or phase end |
| `C` | The plan's measurement-gate movement | Tier 1 per bucket and the seeded 64 B+ sample, from `07.1-CURVE.md` |

`measure_train.py` in this directory gives `L`, `T`, `E` and `US$` for one train:

```
python measure_train.py SESSION FROM TO BASE HEAD
```

A train runs from the plan's dispatch to its last review fix. A main-session message counts when its
timestamp falls in that window, and a subagent by its first message. Plan 07.1-06 writes no Python, so
it stays out of the `L` medians.

## Decision rule

**Size and cost signals.** ±25% is the noise band, and plans are compared on medians:

- Down: median L/M or median E/M is ≤ 0.75× baseline.
- Up: either is ≥ 1.25× baseline.

**Guards, all must hold:**

- Tests: T/L ≥ 0.75× baseline.
- Findings: (CR+BL+WR) per 100 L ≤ 1.25× baseline.
- Defects: no critical defect after close, and D per plan ≤ the worst baseline plan.
- Curve: at least one closed plan moved it, and no two flat plans in a row.
- C side: no tooling commit touches `src/` or `include/`.

**Verdict, computed after plan 2 and at phase end, always labelled indicative, not proof:**

- PAYS OFF: a signal is down, none is up, all guards hold.
- HURTS: any guard fails, or both signals are up. Report to the owner at once.
- INCONCLUSIVE: anything else. After plan 2, propose a paired `/gsd-spike`: no rule vs. YAGNI, on 2-3
  real tooling tasks with hidden tests, run the same day, with a blind judge and the C-side guard after
  every run. It does not run without the owner's OK.

`Y` is reported but decides nothing: it shows the rule leaking, not paying. A phase stopped before two
plans closed gets no verdict.

## Summary

This pass covers the whole phase from `de106376` to HEAD, on top of the six per-plan reviews. It repeats nothing those reviews already dispositioned, and it looked for what only shows across plans.

The main defect is in the slot model. `slots.order_is_known` calls a tie of three or more multi-element arrays known, and wcc386 10.6 does not place them that way. The probe never measured that shape, and the rule went from the model into `search`, the lifter's declaration order, `docs/matching.md` and the watcom-decomp skill. Where the model says "known", the plain declaration moves are switched off, so a wrong answer also removes the fallback.

How the findings were checked:

- CR-01 was measured on the real compiler: `third_party/watcom/10.6/BINNT/WCC386.EXE`, native, both cells, on a small clean-room C file in the session scratchpad. No game code was involved.
- WR-01, WR-02, WR-04, IN-02 and IN-04 were each run against the shipped functions with synthetic input.
- WR-01's and IN-01's real-file counts came from read-only scripts over `orig/` and the objects under `build/batch/`.
- No test suite or docker was run, and nothing was written under `build/`.

None of these findings can land a wrong match. `check` and the gate stay the only judges, and no finding touches them.

## Critical Issues

### CR-01: The slot model is wrong for a tie of three or more multi-element arrays, and it turns off the fallback there

**File:** `tools/reverseapoc/slots.py:38`, `tools/reverseapoc/slots.py:51-59`, `tools/reverseapoc/slots.py:77-78`, `tools/reverseapoc/search.py:571-576`, `tools/reverseapoc/lift.py:649-652`, `.claude/skills/watcom-decomp/SKILL.md:68`, `docs/matching.md:73`, `probe/README.md:125`
**Introduced by:** `40de0d56` (07.1-02), and carried into the lifter by `e28fbb86` (07.1-03)

**Issue:** `order_is_known` returns True for any frame of one size, 1, 2 or 4 bytes. It never looks at what the locals are. The probe's only arrays in such a tie are one-element ones (`char b[1]`, `short b[1]`, beside scalars), so the rule was never measured on `char[4]`, `short[2]` or `char[2]`. Measured with every local address-taken, offsets listed first declared to last:

| Locals | wcc386 10.6 | `frame_layout` |
|---|---|---|
| `char[4]` x3 | 4, 8, 0 | 8, 4, 0 |
| `char[4]` x4 | 4, 0xC, 8, 0 | 0xC, 8, 4, 0 |
| `unsigned char[4]` x3 | 4, 8, 0 | 8, 4, 0 |
| `short[2]` x3 | 4, 8, 0 (`-4r -s -fpi`; my reader could not follow `-oneatx` here) | 8, 4, 0 |
| `char[2]` x3 | 0, 8, 4 | 8, 4, 0 |

The result is the same in both cells and depends on position only, as `pr_tie_three` does: reversing the declarations gives the same offsets by place. From 3 up to 14 locals every count of these three array types disagrees with the model. These shapes do agree with it:

- plain `int`, `char`, `short` and `char *`, and `int[1]`, `char[1]`, `short[1]`, for 2 to 14 locals;
- `char[4]` x2 alone;
- `char[4]` with `int` or `int[1]` locals, in frames of three.

So the line runs through multi-element arrays, not through size. That contradicts the module's own rule, "an offset the probe proves wrong is worse than none" (`slots.py:72-73`).

The effects reach three places:

- **`search`:** `declaration_axis` takes the computed path and yields at most one order, and `declaration_moves` never runs. Running the shipped axis on the measured layout of three `char[4]`, for all 30 ordered pairs of a current and a target order, it reaches the target in 6 pairs and never in the other 24, even following its own candidates. Example: ours `a,b,c`, original `a,c,b`, and it proposes `c,b,a`. The seeded shuffles would have found every one.
- **The lifter:** it declares address-taken slots as `char s_x[N]`, and `lift.py:649` sorts them on the stated assumption that the first declared sits highest (`tests/test_lift.py:233` pins `char s_c[4];`). Three such slots of one size is the refuted shape, so the draft starts in the wrong order.
- **Agents:** `SKILL.md:68` tells a session that declaration order "breaks ties ... when the frame has one size, of 1, 2 or 4 bytes" and that the first declared sits highest. The docs say the same. An agent swapping two `char[4]` locals on that rule moves them somewhere else.

On disk, 2 of 919 converter drafts under `build/batch/run/` hold this shape today, so the reach is small. The model is still wrong, and it is wrong silently.

**Fix:** carry the shape into the model and refuse it, then measure it.

```python
@dataclass(frozen=True)
class Local:
    name: str
    size: int
    scope: int = 0
    array: bool = False  # more than one element: such a tie does not follow M2

def order_is_known(locals_):
    if sum(local.array for local in locals_) > _MEASURED_ARRAYS:  # 2: `char[4]` x2 held
        return False
    ...
```

`memory_locals` sets `array` from the declarator's dimensions: an element count above 1. Then:

- add the table's shapes to `probe/cg_slots.c` and to `TIES` in `tests/test_slots_real.py`;
- measure two arrays beside two or more scalars before trusting that case;
- correct the rule in `slots.py`, `docs/matching.md` and `probe/README.md`, and in `SKILL.md` through `writing-skills`;
- decide whether the lifter should declare a 4-byte taken slot as `int` or `int s[1]`, which does follow M2, and re-measure the curve if so.

## Warnings

### WR-01: A tie the original holds at shifted offsets empties the axis instead of falling back

**File:** `tools/reverseapoc/slots.py:98-99`, `tools/reverseapoc/search.py:517-527`, `tools/reverseapoc/search.py:574-576`
**Introduced by:** `40de0d56`; the `_places_all` fix in `b76b6b19` covers only the lower bound

**Issue:** `_places_all` says each local stays "inside the frame", but it checks only `start + min(moved) < 0`. A target above the layout passes, then `declaration_order` compares `frame_layout(order) == target`, fails on the offset and returns None. `declaration_axis` treats None as "nothing to do". The module docstring says the plain moves stand wherever the model cannot say.

Run on the shipped code, `int a; int b; take(&a, &b);` with a map that swaps the pair above 8 bytes ours lacks, `SlotMap(((0, 12), (4, 8)), True, 8, 20)`, yields `[]`. The swap the original needs is a legal move, and the same swap at offsets 0 and 4 yields one candidate. `test_declaration_axis_yields_nothing_when_size_rules_the_target_out` pins only the case where size really rules the target out.

**Fix:** tell apart "no order can reach this" from "the model cannot place this". Compare relative order inside each tie, or give up to the plain moves when the target is not a permutation of the layout's own offsets:

```python
if set(target.values()) != set(slots.frame_layout(memory).values()):
    yield from declaration_moves(text, span)
    return
```

The size test keeps passing, because its target is a permutation of the layout's offsets.

### WR-02: A declaration the line reader cannot see leaves `_readable` true

**File:** `tools/reverseapoc/search.py:80-83`, `tools/reverseapoc/search.py:487-508`
**Introduced by:** `40de0d56`

**Issue:** `_readable` promises that "every local has a size and a name", but it reads only what `_declaration` recognises. Three legal C89 forms are not recognised at all, so they are not refused:

- `int volatile v;`
- `int (*p)(int);`
- a declarator list split across lines, `int v,` then `w;`

With `take(&a, &b, &v)` and any of the three, `memory_locals` gives `['a', 'b']` and `_readable` gives True, although `v` holds a slot. The computed path then runs on a frame that omits a memory local, and the plain moves are off. The lifter never writes these forms, but `search` takes any FILE, including an agent's hand-written C.

**Fix:** make the reader fail closed. Any line in the block's declaration area that starts with a type word and is not a `_declaration` makes the frame unreadable. A cheaper check also works: refuse when `&name` in the body names a word that is neither a known local nor a parameter.

### WR-03: A slot-only difference on a row with trailing filler is class `size`, so it never routes to the search

**File:** `tools/reverseapoc/classify.py:90-105`, `tools/reverseapoc/classify.py:147-148`
**Introduced by:** `d7e8c1a4` (07.1-04)

**Issue:** `_class_of` compares our trimmed function (`Defined.size` drops trailing filler) with the whole row, filler included. `_strict_prefix` catches only a body that is otherwise identical. Any other difference on such a row makes the masked token lists differ in length, so every mask fails and the row falls through to `unmasked`, which is `size`. Synthetic pairs built like `tests/test_classify.py`'s:

- `body(LOAD_SLOT_4)` against `body(LOAD_SLOT_8) + FILLER` gives `size`, where the same pair without filler gives `slot`;
- `body(MOVE_EBX_TO_EAX)` against `body(MOVE_EBX_TO_EDX) + FILLER` gives `size`, not `register`.

So `route` can never send a filler-tailed row to `search`, though `judge` accepts that same filler as no difference at all. No test pairs a difference with a filler tail, and `docs/toolchain.md:416` says `size` means "another length no mask explains", which is not true here: the filler explains it.

This is not 07.1-04's WR-03, which ruled on what `size` means when no mask fits. Here a mask does fit, once the filler is out.

On disk, 455 of the 759 not-exact committed objects under `build/batch/run/` sit on rows ending in filler. Cutting the filler moves only a few of them today: one to `branch`, one to `tail`, 26 between `size` and `mixed`, and none to `slot`. Rows with slot-only differences are rare now, so the impact is small, but search-improved rows are exactly what would hit this.

**Fix:** cut the original's trailing filler instructions before comparing, in `_class_of`, keeping `classify_pair`'s contract:

```python
insns = list(decode(theirs, start))
while insns and batch.is_alignment_filler(insns[-1]):
    insns.pop()
theirs = theirs[: sum(insn.size for insn in insns)]
```

Add a pinned test for each class with a filler tail.

### WR-04: A slot pair can hold None, which crashes the search's output

**File:** `tools/reverseapoc/batch.py:396-398`, `tools/reverseapoc/cli.py:1286-1288`, `tools/reverseapoc/search.py:513`
**Introduced by:** `ba6bd6a0` (07.1-01)

**Issue:** `slot_map` filters only `our_slots[i] is not None`. `framed` is decided per side, so when ours opens an ebp frame and the original does not, an aligned instruction with a relocated field masks to the same `[ebp - N]` token on both sides, yet only ours has a slot. The pair is `(-8, None)`.

Run on synthetic bytes, `slot_map` returns `pairs=((-8, None),)` with `bijection=True`, and the print at `cli.py:1288` raises `TypeError: unsupported format string passed to NoneType.__format__`. Two such pairs sharing a first element raise inside `sorted(pairs)`, and `_moved` raises on `theirs - ours`. TypeError is in neither `_ERRORS` nor `_UNREADABLE`, so it is a traceback, and from `_slots` it ends the search mid-walk. It needs ours framed and the original not, so it is rare under the current rules, but the map's docstring says it "reports and decides nothing".

**Fix:**

```python
pairs = {(our_slots[i], their_slots[j]) for i, j in aligned
         if our_slots[i] is not None and their_slots[j] is not None}
```

## Info

### IN-01: A conditional tail jump kills eax on the path that falls through

**File:** `tools/reverseapoc/lift.py:496-498`
**Introduced by:** `8761db62`, moved from the spike

**Issue:** `liveness` gives a tail jump the def set `{"eax"}` as it does a call, and `_tail_jump` is true for a `jcc` too. Only the taken path leaves, so eax read on the fall-through path reads as dead before the jump. The rows the converter can read hold 173 conditional tail jumps, and at 34 of them eax is live past the jump and removed this way. Removing the def changes no draft of the 80 rows that hold one, under the census on disk, so the effect today is nil. The census itself was not rebuilt with the fix: `after` feeds `used`, so a rebuild could differ.

**Fix:** `{"eax"} if ci.mnemonic in ("call", "jmp") else set()`.

### IN-02: A byte write over a known word reads as the whole register

**File:** `tools/reverseapoc/lift.py:778-782`
**Introduced by:** `a62ecb3f` (07.1-05)

**Issue:** `over_zero` accepts `old.written > 0 and not old.partial` without comparing widths. After a full-known `ax`, a write of `al` gives `partial=False`, `written=1`, `const=5`: the run reports `eax` as 5, though `ah` still holds the word's high byte. Run on `Block_.set` with `0x1234` in `ax`. The direct note prints `al=5`, which is true, but a value derived from it after that is not marked a guess, and `docs/toolchain.md` says such a value is left out.

**Fix:** require `old.written <= size` in the second half of `over_zero`.

### IN-03: `switch` indexes `compared` directly, which a hole on the guard leaves unset

**File:** `tools/reverseapoc/lift.py:1417`, `tools/reverseapoc/lift.py:1435-1439`
**Introduced by:** `de781d9c` (07.1-03)

**Issue:** `jcc` runs `flush` before it records `compared[jump]`. With `holes=True`, an `Unliftable` from that flush becomes a hole, and the table jump after it raises KeyError, which `Block_.attempt` does not catch. `call_notes` then loses every note of the row to `_register_notes`' broad handler. This is by reading only: the curve shows 0 crashes on the sample.

**Fix:** `self.lf.compared.get(ci.address)`, and treat a missing value as a guard that did not fold.

### IN-04: `reverseapoc lift` is documented as writing nothing, and it writes the census

**File:** `docs/toolchain.md:424`, `tools/reverseapoc/lift.py:1748-1750`
**Introduced by:** `06bd9d13` (07.1-03)

**Issue:** The doc says the verb "writes nothing". With no valid `build/lift/result-used-<stem>.json`, `signature` reaches `result_used`, which walks every game row of the EXE and writes that file.

**Fix:** say so in the doc: the first run builds and caches the census under `build/lift/`.

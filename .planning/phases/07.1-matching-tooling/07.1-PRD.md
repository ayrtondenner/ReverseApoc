# Phase 7.1: Matching tooling (owner scope)

Owner: ayrtondenner, 2026-11-03. Everything here is a locked decision. It comes from the owner's
queued scope (2026-11-01) and the 2026-11-03 kickoff.

## Why

Spike projections put functions of 256 B and up (about 445 of them) on the critical path, and agents
fail there on stack slots, registers and types. The target is about 6-8 weeks to Tier 1 matched. This
phase builds the tools that move that number.

The start gate is met: 07-48, 07-48b and 07-48c are merged with CI green, and flag proposals F-0045 to
F-0057 are landed or held. F-0047 stays held on Watcom E1129 and is out of scope here.

## The six plans, in this order

New code goes in `tools/reverseapoc/` beside `batch.py`. Extend batch and judge, never fork them.

1. `reverseapoc search EXE ADDR FILE`: a declaration-order, scope and type permutation search. About
   600 compiles per function, through `batch.compile_batch`. The score masks stack offsets first, and
   the tool reports the slot map.
2. A wcc386 10.6 stack-slot model (`-4r -s`, `-4r -oneatx -s`), calibrated on our clean-room `probe/`
   only.
3. Converter v1: spike 010's `lift.py` moved to `tools/`, plus holes, ah/dh bytes, switch tables, stack
   structs, setcc/sbb, x87, a short hint and an idiom check. Fix the KeyError on jumps to filler.
4. A failure classifier (register/slot/branch/tail/size) that routes each function to the converter,
   the search or an agent.
5. Disassembly view upgrades: jump-table case targets, and the register value at each call (terminal
   only).
6. The watcom-decomp skill, updated through superpowers' `writing-skills`. **Owner checkpoint first:
   show the curve.**

Plans are sequential: each depends on the one before it. Plan 6 is `autonomous: false`, and its first
task is the owner checkpoint.

## Measurement gate, after every plan

- The converter over all of Tier 1 (exact count per bucket), plus a fixed, seeded 64 B+ sample with the
  seed and rows committed.
- Recorded in the SUMMARY and in `07.1-CURVE.md` in this phase directory.
- Plan 1 opens by recording curve point 0, so movement has a base.
- A tool that moves neither number is not polished.
- **Stop the phase after two plans in a row that move nothing.** Every plan's closing task checks this.

## Rules for the whole phase

- No matching nights while 7.1 code is being written or tested.
- Search matches use the trailer `Matched-By: reverseapoc search`.
- Reused code from brotchie/daggerfall-decomp or abdulahmad/NHL95PC: allowed, and reuse is the default.
  Each copied or adapted file keeps a header naming its origin repo and path, as `check.py` does for
  Theme Hospital and `relocs.py` for KKND, with a row in `docs/tools.md` and a line in `docs/legal.md`
  and the README's credits. Read their code through a scratch clone and never run it. Subagents have no
  network, so the main session fetches it into a fresh scratch directory for them.
- Plans run on the main checkout, by the recipe: `<precondition>` requires `git-dir == git-common-dir`,
  with the temporary `git.allow_default_branch_commits`, `dispatch-isolation --force-isolation none`,
  and a sequential prompt with a bound `<project_root_pin>`. Never run the host and container suites at
  the same time.
- Dispatched agents never push and never use the network.

## Item A: YAGNI is applied (carried in every plan as tasks or verification steps, not advice)

- Each plan's `read_first` lists `.claude/rules/tools.md` (its "YAGNI: scope, not effort" section) and
  `docs/ceremonies.md`.
- Tasks build only what the plan asks for.
- Each SUMMARY has a one-line-per-item "Seen, not built" list.
- Each plan has a code-review task that records YAGNI breaks as `IN-` findings: an unrequested option or
  flag, a single-implementation abstraction, or code written for later. Otherwise the review prompt is
  unchanged: YAGNI never makes a review shorter.
- YAGNI never applies to C or headers (`.claude/rules/src.md`). C produced by the 7.1 tools lands only
  through the gate, as match commits.
- A tooling commit changes nothing under `src/` or `include/`. Each plan has a verification step that
  runs `git diff --stat <commit>^ <commit> -- src include` for every tooling commit and expects it empty.

## Item B: measure whether it pays off (carried in every plan)

The rule is `07.1-YAGNI-MEASURE.md` in this directory, written before planning and never edited.

- Each plan's closing task records its row in `07.1-YAGNI-RESULTS.md`: `L`, `T`, `M`, `E`, `US$`,
  findings by severity, `Y`, `D` so far and `C`, using `measure_train.py`.
- `must_haves.truths` in each PLAN frontmatter is `M`, so state it honestly and do not pad it.
- After plan 2, the closing task computes the verdict from the rule and reports it. An INCONCLUSIVE
  verdict proposes the paired spike and does not run it.
- The tooling must still move the curve.

**What the planning probe found, honestly.** A read-only probe on main (interfaces) suggests the four rows are probably
not wrong boundaries:
- **Each B is a function in C terms.** It is called (0x00061F50, 0x0009A5D0), jumped to as a tail call by other rows
  (0x00061F50), or has its address pushed or stored by code (0x00051DA0 twice, 0x000B78D0). 0x0009A5D0 is also an
  [[entry]] (D-31).
- **So each A is most likely a C function whose last statement calls B.** Watcom dropped the tail jump because B is laid
  out right after A.
- **The project already knows this behaviour.** units.py's docstring (05-RESEARCH Pattern 4) says Watcom "lets one
  [function] fall through into the next".
- **07-29 showed it in practice (F-0005).** The C that hit func_00061F30 at 100% under `-4r -ot` matched only while
  func_00061F50's C followed it in the same file. With func_00061F50 back as INCLUDE_ASM, the target fell to 68.57.

A merge would leave those calls, jumps and pointers aimed into the middle of a row, which no C source can produce. The
gate could then never match the row. So the plan does not assume merges. It:
1. builds the detector and runs it over both EXEs (the full set, not just 4 rows);
2. tests the fall-through hypothesis with a clean-room compile in the container;
3. shows the owner every pair with its evidence and what each option would change.

The owner then rules each pair:
- `keep`: the boundary is right, and the owner gives A a verdict, `c` for C that falls through;
- `recut`: A and B stay separate rows but move into one unit, because a compiler drops a tail jump only inside one module.
  0x0009A5B0 sits in u_0009a420 and 0x0009A5D0 starts u_0009a5d0;
- `merge`: only for a `label` pair, where B has no function evidence.

Decisions taken here, with their reasons:
- **The detector is a new read-only verb, `mechanics splits`, in a new module splits.py.** Like `mechanics asm`, it is
  D-23 evidence. It reads orig/ and the committed config and writes nothing, and mechanics.py does not import it (no
  cycle with asmclass). It reuses asmclass.TERMINATORS and the content data tags, so a pair's A is exactly an asm-list
  `no-terminator` row.
- **The existing override cannot merge these rows.** boundaries.csv holds only Ghidra/capstone disagreements. A hand
  verdict there survives only where the D-07 rule leaves the address undecided (`functions._apply_verdicts`), and every B
  here is decided by LE evidence (`fixup` or `call`), with verdict `rule`. Some B rows (0x00061F50, 0x0009A5D0) are not
  disagreements at all.
- **So a merge, if ruled, needs a new owner-written input, config/<exe>/merges.csv.** `reconcile` drops each listed
  start, and the D-07 end rule then runs the row before it through B. It is built only when the owner rules at least one
  merge (Task 4). Without a merge the generator gets no input that nothing uses. The owner's ruling is the missing
  information that decides it.
- **A recut uses the documented override.** units.csv is a draft that is "re-cut by hand (reason `hand`)" (D-11), and
  `functions --write` re-assigns the unit column from it (assign_units). So the drift tests hold.
- **Guards keep matched code and signed data safe.** A merge is refused when:
  - B or A is matched in status.csv, or B has any status.csv row;
  - B has a symbols.csv name;
  - B is an [[entry]] (D-31) or a runtime or entry start;
  - B has function evidence (any call, unconditional jump from another row, or taken address), so only a `label` pair
    can merge;
  - A and B are in different units;
  - their unit has a committed src/ file (its INCLUDE_ASM marker for B would then be stale).

  A recut is refused when a moved row has a status.csv row or its unit has a committed src/ file. Each refusal is a STOP
  for the owner, never an edit.
- **Held rows get the owner's verdict whatever the pair ruling (scope item 4).** If a merge makes the detector stop
  proposing A, `mechanics asm --write` drops A's list row, and the ruling is recorded as moot. Otherwise the owner's
  verdict applies. Ruling `c` or `asm` on every held row brings the held count to 0 in every tier and in the dry run.
- **Digests and re-signs (F36).**
  - The [asm_list] re-sign is always needed, because verdict cells change.
  - A tier re-sign is needed when its digest moves. Any verdict change into or out of `asm` on a row the tier reaches can
    move it:
    - into `asm` takes the row, and every row reached only through it, out of must-match;
    - out of `asm` puts them back. This is the case of a 07-44 conflict row re-ruled `c` or `unclear`: the row and the
      rows reached only through it become members again, labelled `readded` in 45-signoff.txt;
    - a merge that removes a member row moves it too.

    stops at a hub), and a recut (mechanics.py and callgraph.py read no unit). 45-signoff.txt asserts each of these and
    names any tier that moved anyway. Such a tier is handled like any other moved tier: shown at Task 6 and re-signed.
